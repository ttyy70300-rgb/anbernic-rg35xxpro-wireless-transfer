## 一、为什么要写这份文档（一次误判的复盘）

### 1.1 误判经过

用户问：「我这台为啥是 Ubuntu？你是从哪里读到这个信息的呢？」

第一次核实，我读到了这些：

```
/etc/os-release   → PRETTY_NAME="Ubuntu 22.04 LTS"
apt-get / dpkg    → 存在，已装 1284 个 deb 包
apt 源            → mirrors.tuna.tsinghua.edu.cn/ubuntu-ports/ jammy
```

然后我**做了一个错误的推断**：

> ❌ 「原厂 Anbernic 固件通常不会保留 apt 源 + 1289 个包…
>    所以这是一台被人为刷写、深度定制过的 Ubuntu，很可能是社区魔改包。」

### 1.2 用户更正

> 「这就是我刷的官方给的最新的包。我从官方客服那里要来的」

### 1.3 错在哪 —— 探测方法的硬伤

| # | 我的错误推理 | 实际 |
|---|---|---|
| 1 | 有 `apt` + 1284 个包 ⇒ 被人魔改 | **官方固件本来就带完整 apt 用户空间**，这是 Anbernic 的设计选择（方便用户自己装包） |
| 2 | apt 源指向清华 ⇒ 第三方配置的 | **厂商预配的国内镜像**，国内厂商标配 |
| 3 | 只看了「用户空间长什么样」 | **没看盘面里的厂商印记** —— 而厂商印记是最硬的证据 |

**核心教训**：

> **判断固件来源，要看「厂商有没有留下印记」，而不是「用户空间像不像原厂」。**
> 用户空间的裁剪策略是厂商的自由选择，不能作为判据。

## 二、官方固件的铁证链（8 项）

### 铁证 1：厂商版本文件 `version.ini`

```
$ cat /mnt/vendor/oem/version.ini
20260522
```

**`/mnt/vendor/oem/version.ini` 是 Anbernic 的出厂版本标识文件**，值是 **`20260522` = 2026-05-22**。

`/mnt/vendor/oem/` 目录下三个文件构成一个完整的「出厂身份三件套」：

| 文件 | 内容 | 时间戳 | 作用 |
|---|---|---|---|
| `board.ini` | `RG35xxPRO` | 2025-04-09 12:20 | 机型标识（launcher 据此选 UI 分支） |
| `language.ini` | `0` | 2022-06-01 00:58 | 出厂语言（0 = 简体中文） |
| `version.ini` | `20260522` | 2022-05-30 23:48 | **固件版本号** |

### 铁证 2：全盘同日期批量构建 —— `2026-05-22`

这是**一次完整固件构建出厂**的典型特征：

```
/mnt/vendor/oem/            → 2026-05-22 08:59 (lost+found)
/mnt/vendor/bin/dmenu.bin   → 2026-05-22 08:36
/mnt/vendor/bin/muos1.bin   → 2026-05-22 08:38
/mnt/vendor/bin/muos2.bin   → 2026-05-22 08:44
/lib/modules/4.9.170/       → 2026-05-22 08:53
/lib/modules/mali_kbase.ko  → 2026-05-22 08:53
```

**厂商打包时统一刷了时间戳**。这 6 个文件横跨两个不同分区（p6 vendor 和 p5 root），却在同一天上午的 20 分钟内集中出现 —— 只有镜像打包能做到。

### 铁证 3：内核构建者主机名

```
$ cat /proc/version
Linux version 4.9.170 (flower@flower-B85M-D2V)
  (gcc version 5.3.1 20160412 (Linaro GCC 5.3-2016.05))
  #32 SMP PREEMPT Tue May 12 09:39:47 CST 2026

$ uname -v
#32 SMP PREEMPT Tue May 12 09:39:47 CST 2026
```

- **`flower@flower-B85M-D2V`** —— 内核编译者的用户名 `flower` + 主机名 `flower-B85M-D2V`
- `B85M-D2V` 是**技嘉主板的型号**，说明这是厂商工程师的**普通办公 PC 编译机**
- 构建时间 **2026-05-12**，比固件版本号 `20260522` 早 10 天 —— **先编内核，后打包固件**，时间线完全自洽
- 内核版本 `4.9.170`，Linaro GCC 5.3.1（Allwinner BSP 的标准搭配）

> String `flower` 是 Anbernic H700 固件的**已知常量**（社区固件分析资料中多次出现），
> 可作为该厂商内核的确证指纹。

### 铁证 4：内核模块与内核版本严格对应

```
/lib/modules/4.9.170/mali_kbase.ko   (17,589,960 bytes, 2026-05-22 08:53)
```

- 内核 `4.9.170`，模块路径 `/lib/modules/4.9.170/` —— **版本号严格对应**（交叉编译错版本会加载失败）
- `mali_kbase.ko` 是 ARM Mali GPU 内核驱动（H700 的 GPU 是 Mali-G31）
- 这是**厂商 BSP 包**里才有的东西

### 铁证 5：`dmenu.bin` 是厂商自研启动器

```
/mnt/vendor/bin/dmenu.bin   225,710 bytes   2026-05-22 08:36
```

- **静态链接**（`ldd` 报「不是动态可执行文件」）
- 字符串含 `/dev/disp`、`/dev/ion`、`CdcIonAlloc`、`DisplayEngine Frequency`
- 退出时不做 `DISP_BLANK` 清理（→ DispEngine 图层残留）
- **静态链接 + 直接用 Allwinner 私有 IOCTL = 厂商原生实现**，第三方拿不到这套源码

### 铁证 6：Ubuntu 用户空间时间戳是 2022 年

```
/etc/issue       → 2022-04-18 10:28
/etc/lsb-release → 2022-04-18 10:28
/etc/os-release  → 2022-04-18 10:28  (→ ../usr/lib/os-release)
/usr/bin/ 目录   → 2022-05-31 20:58
/usr/            → 2024-06-13 06:14
/                → 2022-06-11 05:32
```

**这解释了为什么 os-release 是 2022 年** —— 厂商用的是 **Ubuntu 22.04 官方 rootfs 快照（2022 年 4~6 月）**，
在此之上叠加自己的 BSP 和 vendor 内容。用户空间的时间戳保留着原始 rootfs 的痕迹。

### 铁证 7：`launcher.sh` 挂在 SysV init.d 里

```
/etc/init.d/launcher.sh   1146 bytes   2025-12-05 03:24

/sbin/init -> /lib/systemd/systemd
systemd 249 (249.11-0ubuntu3)
```

- `launcher.sh` 是**厂商自己加进 `/etc/init.d/` 的启动脚本**（不属于任何 deb 包）
- systemd 以 **SysV 兼容模式**拉起它（`systemd-sysv-generator`）
- `2025-12-05` 的日期说明这条启动链在 2025 年底定稿

### 铁证 8：`/mnt/vendor/` 目录结构是厂商专属

```
/mnt/vendor/
├── bin/         厂商二进制（dmenu.bin / default.ttf / 各 .dge 工具）
├── ctrl/        控制脚本（2026-04-03）
├── deep/        深度配置
├── lib/         厂商库（2025-11-14）
├── oem/         出厂身份三件套
├── res1/ res2/  厂商资源（主题/图标/音效，22 个子目录）
├── res3/ res4/  更多资源
└── lost+found/  ext4 分区痕迹
```

`res1`～`res4` 四个资源分区、`ctrl`/`deep` 这类命名 —— **这是 Anbernic 固件的成套设计**，
不是个人刷机者会搭的结构。

### 4.2 ★ SDL2：**这台机器里有两个不同版本的 SDL2**（重要更正）

之前文档里统一写「SDL2 2.0.12」—— **对 pysdl2 通路是不准确的**。实测：

```
dpkg 包：libsdl2-2.0-0:arm64  版本 2.0.20+dfsg-2ubuntu1.22.04.1

① /usr/lib/libSDL2-2.0.so.0
      → libSDL2-2.0.so.0.12.0        ← SDL 2.0.12，4.9 MB
      用途：原厂 dmenu.bin 静态链接进去的那份

② /usr/lib/aarch64-linux-gnu/libSDL2-2.0.so.0
      → libSDL2.so → libSDL2-2.0.so.0.2800.5   ← SDL 2.28.5，2.7 MB
      用途：★ pysdl2 运行时实际加载的这份

实测 SDL_GetVersion() → 2.28.5
实测 ctypes.util.find_library('SDL2') → libSDL2-2.0.so.0 → 解析到 ②
```

**对开发的意义**：

| 通路 | 实际用的 SDL2 | 备注 |
|---|---|---|
| 我们的 Python 程序（pysdl2） | **2.28.5** | 新版，行为按 2.28 系列预期 |
| 原厂 `dmenu.bin` | **2.0.12**（静态） | 与我们无关 |
| C 程序动态链接 `-lSDL2` | 取决于 `-L` 路径 | **两个都在，链接时要注意选哪个** |

> ⚠️ **2.0.12 → 2.28.5 之间有 12 年上游演进**。
> `SDL_HINT_RENDER_SCALE_QUALITY`、`SDL_WINDOW_FULLSCREEN_DESKTOP` 等行为在不同代之间可能有差异。
> 排查渲染问题时要先确认用的是哪一份。

### 4.3 显示层（已确证）

- 显示子系统是 **Allwinner DispEngine 多图层合成器**（`/dev/disp`），**不是单一 framebuffer**
- `/dev/fb0` 只是**最底层图层** → 裸写 fb0 会被上层残留图层完全盖住
- 原厂应用与我们的程序**都必须走 SDL2**（SDL 内部 open `/dev/disp` 建顶层图层）
- dmenu 运行期间：fb0 报 `1280×1024 16bpp`
- 应用运行期间：`SDL_GetRendererOutputSize` 返回 **640×480**
- SDL2 视频驱动：`b'mali'`（唯一真实）+ `b'dummy'`

### 4.4 输入设备

| 设备 | 内容 |
|---|---|
| `event0` | 仅 `KEY 116 (POWER)` |
| **`event1`（主力）** | `EV_KEY`: 304A/305B/306Y/307X/308L1/309R1/310SELECT/311START/312MENUF/314L2/315R2/114V+/115V-<br>`EV_ABS`: 2(ABS_Z)/3(ABS_RX)/4(ABS_RY)/5(ABS_RZ)/16(ABS_HAT0X)/17(ABS_HAT0Y) |

**摇杆方向走 `EV_ABS`**：`ABS_RX`(3) 水平 / `ABS_RY`(4) 垂直，值域约 ±3700，中心 0，负值为补码（`4294963596` = `-3700`）。

### 4.6 启动与部署契约

```
systemd
  └─ /etc/init.d/launcher.sh (SysV 兼容)
       └─ loadapp.sh
            └─ dmenu_ln  (前台跑 /mnt/vendor/bin/dmenu.bin)
                 ├─ 用户选中 → 把命令写入 /tmp/.next → dmenu 退出
```

- dmenu 的关闭信号是 **`SIGUSR1`**（`/etc/init.d/launcher.sh:45`），**SIGINT 无效**
- 应用部署目录：`/mnt/mmc/Roms/APPS/<应用名>/`（TF 卡上）
