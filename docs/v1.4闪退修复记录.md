## 一、闪退根因（按影响排序）

### 主因：`launcher.sh` 调用 `setmode.py` 强切显示模式

上一版启动流程：

```bash
python3 "$APPDIR/setmode.py"    # ← 罪魁祸首
python3 "$APPDIR/main.py"
```

`setmode.py` 用 `FBIOPUT_VSCREENINFO` 把显示切成 640×480 32bpp。实测行为：

| 步骤 | 结果 |
|---|---|
| `FBIOPUT_VSCREENINFO` 返回 | **0（成功）** |
| 紧接着 `FBIOGET_VSCREENINFO` 读回 | **返回新值 640×480 32bpp** |
| `cat /sys/class/graphics/fb0/virtual_size` | **仍是旧值** |

也就是说 —— **写回被接受了，但驱动实际没换模式**。显示时序由 `disp` 驱动独立控制，
改 `fb_var_screeninfo` 只是改了软件视角。

**后果链条**：

```
main.py 读到 width=640, height=480
        ↓
mmap 长度 = 640 × 4 × 480 = 1,228,800 字节
        ↓
但驱动实际仍是 1280×1024，stride = 2560 字节（远大于 640×4）
        ↓
按 line_px 步进写第 y 行 → 目标偏移超出 1.2MB 映射范围
        ↓
SIGBUS → 进程被内核立刻杀死
        ↓
用户看到：点进去 → 黑一下 → 回到菜单（闪退）
```

**修复**：**删掉 `setmode.py` 的调用**，永不切换显示模式，只按运行时读到的参数作画。
`setmode.py` 已改名为 `setmode.py.DISABLED`。

### 次因 1：`launcher.sh` 缺少 `PYSDL2_DLL_PATH`

原厂 5 个应用的 `.sh` 都有一行 `export PYSDL2_DLL_PATH="/usr/lib"`。上一版漏了。
fb.py 本身不依赖它，但缺了会让环境与原厂不一致，为后续埋坑。已补上。

### 次因 2：崩溃无任何痕迹

原厂把应用的 stdout/stderr 丢进 `/dev/null`。上一版 `main.py` 直接
`from PIL import Image`，一旦失败就是静默退出，屏幕上什么都不显示。
用户只能看到"闪退"，无法提供任何线索。

**修复**：新增 `boot.py`（防闪退诊断层，见下）。

### 次因 3：启动脚本用 `mkdir -p` + `exec >` 覆盖式重定向

- `mkdir -p "$APPDIR"` —— 应用目录由用户从 PC 拷入，脚本不该自己创建。
  路径不对时会静默建出空目录，掩盖"发布包不完整"这个真实问题。
- `exec > "$LOG"` 会截断历史日志，出问题时看不到上一次的痕迹。

**修复**：去掉 mkdir，日志改追加 + 超 256KB 轮转。

### 次因 4：主循环满速空转

`while running:` 里没有任何 sleep，会吃满一个 CPU 核。
在 1GB 内存 / 1.5GHz 的掌机上可能导致系统整体卡顿。

**修复**：固定 30fps 上限 + 单次 sleep ≤5ms 保证按键响应。

## 二、新增：boot.py 诊断层

### 为什么需要

"闪退"这种失败模式在嵌入式设备上极难调试：没有屏幕输出、没有串口、
用户也不方便跑 SSH。**必须让程序自己把错误画到屏幕上。**

### 设计约束

| 约束 | 原因 |
|---|---|
| **只用标准库** | 必须在 Pillow 等依赖之前就能工作。Pillow 缺失本身就是要报的错之一 |
| **绝不 import 本项目其他模块** | 避免循环依赖；fb.py 有 bug 时它仍能用 |
| **任何失败都不再抛异常** | 兜底层自己崩了就完全失去意义 |
| **不改任何系统状态** | 只 mmap 已存在的 `/dev/fb0` 写像素 |
| **内嵌点阵字** | 不能依赖字体文件（字体缺失也是要报的错之一） |

### 双轨输出（关键设计）

点阵字只能画 ASCII，画不了中文。所以 `die()` 同时接收中文和英文两套信息：

```python
boot.die(
    "图形库 Pillow 加载失败",           # 中文 → 写进 boot.log
    e,                                  # 异常对象 + traceback
    ["本机固件应自带 Pillow 9.0.1。"],   # 中文补充 → 写进 boot.log
    ascii_title="PILLOW LOAD FAILED",   # 英文 → 画到屏幕上
    ascii_extra=["Pillow (PIL) is required but missing."],
)
```

屏幕效果（640×480）：

```
POCKETTRANSFER
STARTUP FAILED
PILLOW LOAD FAILED
PILLOW (PIL) IS REQUIRED BUT MISSING.
STOCK FIRMWARE SHOULD SHIP PILLOW 9.0.1.
MODULENOTFOUNDERROR: NO MODULE NAMED
'PIL'
FILE ".../POCKETTRANSFER/MAIN.PY", LINE 45
PRESS ANY KEY / AUTO EXIT 8S
```

用户看一眼就知道该找谁、该做什么。

### 一个实现细节：小写字母映射

最初点阵字只做了大写。测试时发现 Python 的异常信息
（`ModuleNotFoundError`、`File "main.py"`）几乎全是小写，
屏幕上会变成大片 `?`，关键信息直接读不出来 —— 兜底屏等于白做。

**修复**：小写字母映射到大写字形。有专门的测试守住这条（`selftest.py`）。

## 三、fb.py 的加固

### 新增参数自洽校验

```python
# 历史上出现过「GET 返回已切换的新值、但驱动实际仍用旧 stride」的情况，
# 此时按新 width 作画会写越界 → SIGBUS → 进程瞬间消失。
if self.line_px < self.width:
    raise FramebufferError(
        f"行宽不自洽：line_px={self.line_px} < width={self.width}，"
        f"显示参数不可信，拒绝继续（否则会写越界）")
```

宁可拒绝启动并报错，也不写越界闪退。

### 新增写越界防护

两个快速路径（32bpp / 16bpp）的每行写入前都检查：

```python
limit = len(self.mm)
row_bytes = self.width * (self.bpp // 8)
...
if dst + row_bytes > limit:
    break
```

即使参数意外不对，最坏情况是画面不完整，不会崩。

### 映射长度改用 max()

```python
size = self.line_px * (self.bpp // 8) * self.virtual_h
if self.smem_len:
    size = max(size, self.smem_len)   # 取驱动报告的实际显存大小
```

### libc 延迟加载

```python
def _load_libc():
    if os.name != "posix":
        raise FramebufferError("ioctl 仅能在 Linux 上使用（当前系统不是 posix）")
    ...
```

这样在 PC 上做离线测试时不会因为 `libc.so.6` 不存在而 import 失败。

## 四、启动脚本（launcher.sh）最终形态

```bash
set -u
progdir="$(cd "$(dirname "$0")" && pwd)"
basedir="$(cd "$progdir/../.." && pwd)"   # Roms/APPS -> 卡根
APPDIR="$progdir/PocketTransfer"

export BASE_PATH="$basedir"               # 卡根，程序据此认定管哪张卡
export PYSDL2_DLL_PATH="/usr/lib"          # 与原厂 5 个应用一致
export LD_LIBRARY_PATH="/usr/lib:/mnt/vendor/lib:${LD_LIBRARY_PATH:-}"
export TERM=linux

# 自检：失败时明确报错，不静默退出
[ -d "$APPDIR" ] || fail "找不到应用目录..."
[ -n "$PY" ]     || fail "系统未找到 python3"
[ -f "$APPDIR/main.py" ] || fail "缺少 main.py"

"$PY" "$APPDIR/main.py" >> "$LOGFILE" 2>&1
exit 0
```

**与上一版的差异**：

| # | 上一版 | 本版 | 原因 |
|---|---|---|---|
| 1 | 调 setmode.py 切模式 | **删除** | 闪退根因 |
| 2 | 无 PYSDL2_DLL_PATH | 补上 | 与原厂一致 |
| 3 | `mkdir -p $APPDIR` | 删除 | 掩盖发布包不完整 |
| 4 | `exec >` 覆盖日志 | 追加 + 轮转 | 保留历史 |
| 5 | 无环境自检 | 逐项检查 + 中文报错 | 不静默失败 |

**绝对不做的事**（用户明确的边界）：

- 不 kill 任何进程（尤其 dmenu / dmenu_ln / loadapp）
- 不写 `/tmp/.next`
- 不切显示模式
- 不 remount 文件系统
- 不建软链
- 不写 sysfs

## 缺陷 1（真正的崩溃点）：结构体偏移表整体错位

`fb_var_screeninfo` / `fb_fix_screeninfo` 的字段偏移**全部写错了**。

当时的偏移表（错）与实机真实布局（对）对照：

| 字段 | 错误偏移 | 正确偏移 | 错偏移处实际是什么 |
|---|---|---|---|
| var.xres | 64 | **0** | 0（读出来是 0） |
| var.yres | 68 | **4** | 0 |
| var.bits_per_pixel | 88 | **24** | **height = 94（mm）** |
| fix.smem_len | 8 | **24** | smem_start 低 4 字节 |
| fix.line_length | 56 | **48** | mmio_start = 0 |

于是：
- `bpp` 读在偏移 88 → 读到物理高度 **94mm** → 报「不支持的色深 94bpp」
- `line_length` 读在偏移 56 → 读到 0 → 报「line_length 为 0」

**为什么会错**：早期把「`fcntl.ioctl` 读出的字段错位」误判成调用方式问题，
又凭错误印象认定「必须补 64 字节私有头」，从此偏移表一路错到底。
换成 ctypes 后只是换了调用方式，偏移仍是错的。

**铁证获取方式**（重要，值得复用）：

```bash
python3 /tmp/pfd.py     # tools/probe-fb-deep.py 的实机版
```

把 `fb_var_screeninfo` 的 192 字节**逐字节 dump** 出来，直接读原始字节：

```
 0: 00 05 00 00 | 00 04 00 00 | 00 05 00 00 | 00 04 00 00
    0x500=1280    0x400=1024    1280          1024     ← xres 在偏移 0！
16: 00 00 00 00 | 00 00 00 00 | 10 00 00 00 | 00 00 00 00
    xoffset=0      yoffset=0      bpp=16                  ← bpp 在偏移 24！
...
88: 5e 00 00 00 | 96 00 00 00
    0x5e=94        0x96=150        ← height=94mm, width=150mm
```

fix 的 dump 里偏移 48 = `00 0a 00 00` = **2560** = 正好是 sysfs 的 stride。

**教训**：结构体布局**必须用实机逐字节 dump 验证**，不能靠记忆、不能靠猜。
已经把这个 dump 固化成 `tools/selftest.py` 第 6 节的断言（用原始 hex 做真值回归）。

## 缺陷 2（把错误信息彻底掩盖）：`boot.py` 里有两个 `die()`

`boot.py` 中同时存在两份 `die()` 定义：

| 位置 | 签名 |
|---|---|
| 第 451 行（新版） | `die(title, exc=None, extra=None, wait=8.0, ascii_title=None, ascii_extra=None)` |
| 第 534 行（旧版残留） | `die(title, exc=None, extra=None, wait=8.0)` |

Python **后定义者覆盖先定义者** → 实际生效的是旧版。
调用方传 `ascii_title=` → `TypeError` → 连兜底屏都画不出来 → 屏幕全黑/闪退。

这是上一轮编辑时**追加而非替换**留下的。

**教训**：同名函数只能有一个定义。已在 `tools/selftest.py` 第 7 节加断言：
`boot.py` 中 `def die(` / `def show_error_screen(` / `def log(` / `def checkpoint(`
各只能出现 1 次；并用 AST 校验 `main.py` 里所有 `boot.die(...)` 的实参名都被签名接受。

```
                     U:640x480p-59      ← 驱动支持两种模式，当前用 1280x1024

ioctl 读回（修正偏移后，与 sysfs 自洽）:
    xres=1280 yres=1024 virt=1280x1024 bpp=16
    line_length=2560   virt_w*bpp/8 = 2560  [OK 自洽]
    height=94mm width=150mm
    red/green/blue/transp bitfield 全为 0（驱动未填，按 bpp 推断标准布局）
    smem_len=7372800  smem_start=0xff800000
```

# 附录二：第三次闪退 —— 「画对了却看不见」到「看得见了却再进就崩」（2026-10-05 下午）

> 这是本项目**最曲折**的一段。分两个阶段：
> **阶段 A**：程序跑得好好的，屏幕却显示"加载中"（不是崩溃，是显示模型搞错了）
> **阶段 B**：改用 SDL2 后能显示了，但**退出再进会闪退**（rc=139）

---

## 阶段 A：画对了，却看不见 —— DispEngine 多图层合成器

### 现象

修完前两个缺陷后，用户报告：

> "我点了程序，这个掌机进程序都会显示加载中，这次并没有闪退，
> 而是卡在加载中页面了，确实震动了一下。"

**这就非常迷惑了** —— 震动说明程序起来了，但屏幕是"加载中"（原厂菜单的样式）。

### 排查过程

| # | 检查项 | 结果 | 说明 |
|---|---|---|---|
| 1 | 程序是否在跑 | ✅ 稳定 29.9 FPS | 主循环完全正常 |
| 2 | 写入是否成功 | ✅ 写回自检 0 异常 | mmap + 写入没问题 |
| 3 | 谁持有 fb0 | ✅ 只有我们的进程 | 没有被别的进程抢 |
| 4 | fb0 内容对不对 | ✅ 第 0 页是完整 UI | 画的画确实进了 fb0 |
| 5 | fb0 里有"加载中"吗 | ❌ **全 7MB 里找不到** | ★ 决定性证据 |
| 6 | dmesg | ✅ 280+ 条 `disp_mgr_protect_reg_for_rcq` | disp 驱动在管理图层 |
| 7 | 原厂应用怎么画 | ✅ 全部用 SDL2 `FULLSCREEN_DESKTOP` | 官方示范 |

### 根因

**屏幕内容根本不是 fb0 的内容。** 本机显示子系统是 **Allwinner DispEngine 多图层合成器**：

```
原厂菜单 dmenu.bin ──> open(/dev/disp) + ioctl(DISP_LAYER_SET_CONFIG2)
                       + ioctl(DISP_HWC_COMMIT)
                       ──> 建立一个硬件图层（像素在 /dev/ion 显存里）
                       ──> 退出时不做 DISP_BLANK → 图层残留

我们的程序     ──> mmap /dev/fb0 写像素
                       ──> 写在 disp 的【最底层图层】
                       ──> 被残留的"加载中"图层【完全盖住】
```

**铁证**：fb0 全 7MB 里找不到"加载中" → 那画面在别处（ion 显存 + disp 图层）。

**为什么原厂应用没事**：SDL2 的 `FULLSCREEN_DESKTOP` 会
`open("/dev/disp")` 建**自己的新图层**并置于最顶层，退出时销毁。

### 修复

新增 `handheld/sdl_display.py` —— SDL2 显示后端，**接口与 `fb.py` 完全一致**，
所以 `main.py` 的 UI 代码一行都不用改：

```python
flags = sdl2.SDL_WINDOW_FULLSCREEN_DESKTOP | sdl2.SDL_WINDOW_SHOWN
self.window = sdl2.SDL_CreateWindow(title_b, ..., 0, 0, flags)
self.renderer = sdl2.SDL_CreateRenderer(window, -1, sdl2.SDL_RENDERER_ACCELERATED)
```

`bring_up_display()` 改为：**优先 SDL2 → 回退 fb0**。

同时新增 `_dmenu_running()`：dmenu 还在跑时 SDL 建窗必然失败
（`mali-fbdev: Can't create EGL window surface`），
这是**正常现象**，应**安静退出**而不是弹错误屏。

### 验证

`tools/probe-sdl.py`（独立进程，画彩色横条）从菜单启动 → **8/8 步全通过**。
用户目视确认**看到了彩色横条**，SDL2 通路成立。

## 阶段 B：看得见了，但退出再进会崩（rc=139）

### 现象

用户报告：

> "刚才跑测试的时候，屏幕疯狂闪动，但是之后这个软件就正常显示了！
> 最外层是一圈线，然后四角有四个框。但是，我退出之后，再重进，又闪退了"

（"一圈线 + 四角四个框"就是 `draw_calibration_frame()` 画的校准框，说明显示正常。）

`boot.log` 读到的崩溃现场：

```
[13:01:08] 启动 /mnt/mmc/Roms/APPS/PocketTransfer/main.py
[13:01:11] 显示就绪(SDL2): SDL2 640x480 bpp=32 fullscreen_desktop 渲染器=HW
[13:01:11]   sdl探测 | 输出尺寸 640x480     ← 日志到此为止！
[13:01:11] main.py 退出，rc=139            ← SIGSEGV
```

**日志断在 `输出尺寸 640x480` 之后**，下一行本该是 blit 的结果 → 崩在 `blit()` 里。

### 缺陷 1（主因）：`SDL_CreateRGBSurfaceWithFormatFrom` 收到临时对象

```python
# ✗ 错误写法
surface = sdl2.SDL_CreateRGBSurfaceWithFormatFrom(
    rgba.tobytes(),          # ← 临时对象！
    self.width, self.height, 32, self.width * 4,
    sdl2.SDL_PIXELFORMAT_RGBA32)
```

这个 C 函数**不拷贝数据**，只把 buffer **包装成指针**。
`rgba.tobytes()` 是**临时对象**，没有变量持有它 —— CPython 在调用返回后
**立刻回收它**，而 SDL 仍拿着**悬空指针**去读像素 → **SIGSEGV**。

**修复**：用局部变量显式持有，直到 texture 建好：

```python
buf = key                    # ← 必须持有！引用计数是这里的唯一保障
surface = sdl2.SDL_CreateRGBSurfaceWithFormatFrom(
    buf, self.width, self.height, 32, self.width * 4,
    sdl2.SDL_PIXELFORMAT_RGBA32)
try:
    self._texture = sdl2.SDL_CreateTextureFromSurface(self.renderer, surface)
finally:
    sdl2.SDL_FreeSurface(surface)
    del buf                  # texture 已拷贝数据，此时才可释放
```

**对比佐证**：`probe-sdl.py` 用 `buf` 变量持有，所以它**从来没崩过**。

### 缺陷 2（共犯）：`import sdl2.ext` 污染 SDL 状态

```python
DLLWarning: OSError('/lib/aarch64-linux-gnu/libSDL2_image-2.0.so.0:
                    undefined symbol: SDL_roundf')
```

`sdl2.ext` 会连带加载 SDL2_image / SDL2_ttf / SDL2_mixer。
**本机上 SDL2_image 是坏的**，加载失败会污染 SDL 内部状态，
导致后续渲染调用段错误。

**修复**：`_import_sdl2()` 只 `import sdl2`，**彻底移除** `sdl2.ext`。

### 缺陷 3（诊断手段缺失）：SDL 段错误打不出 traceback

SDL 层段错误时进程**直接消失**，Python traceback 打不出来。
只能靠**每一步都 `write + fsync` 落盘**，看最后一条日志停在哪。

**修复**：`open()` 加 12 个阶段打点，`blit()` 首 3 帧打点：

```python
def stage(msg):
    self._stage.append(msg)
    try:
        import boot
        boot.log(f"  [SDL阶段] {msg}")   # boot.log 内部带 flush + fsync
    except Exception:
        pass
```

## 三次闪退的根因汇总

|---|---|---|---|
| 第 1 次 | 点进去闪退 | `launcher.sh` 调 `setmode.py` 切显示模式 → 写越界 **SIGBUS** | 删除 `setmode.py` 调用 |
