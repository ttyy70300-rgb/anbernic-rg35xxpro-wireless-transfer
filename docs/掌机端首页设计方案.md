# 掌机端首页（Dashboard）设计方案

> 状态：**规划稿，待确认后再动代码**
> 目标版本：PocketTransfer 掌机端 v1.5
> 屏幕：640×480 物理屏（`k = 1.0`）

---

## 一、需求确认

用户原话：

> 「掌机端在现有基础上增加一个首页，我的建议是屏幕分成 3 部分，
> 上面一多半，下面一小半。下面这一半显示掌机端怎么操作，
> 各个按键的定义啥的。上面那一多半，左边展示一些固定信息，
> 我还没想好展示什么，右边那一半展示关键操作日志。」

经过一轮确认，四个关键决定已定：

| # | 决定 | 选择 |
|---|---|---|
| 1 | 首页定位 | **独立页，标签栏扩为 5 个**（首页/状态/文件/网络/日志），开机默认进首页 |
| 2 | 上半左栏内容 | **连接状态为主**（IP/连接/对端/权限/卡根/收发累计） |
| 3 | 右栏日志 | **复用 `log_lines`，只筛关键项**，日志页仍显示全部 |
| 4 | 下半按键说明 | **随当前页动态变化**，永远和实际行为一致 |

### 高度分配（640×480，k=1.0）

| 区块 | 高度 | 占比 | 说明 |
|---|---:|---:|---|
| 标题条 | 34 | 7% | 复用现有 `bar_h` |
| 标签栏 | 28 | 6% | 复用现有 `tab_h` |
| **上半（信息区）** | **~260** | **54%** | ←「上面一多半」 |
| **下半（按键说明）** | **~158** | **33%** | ←「下面一小半」 |
| 底栏 | 28 | 6% | 复用现有 `foot_h` |

`260 : 158` ≈ **62% : 38%**，符合"上多下少"。

**宽度分配**：上半左右**各半**（用户明确说"右边那一半"）。

```
内容区宽 W - 2*pad = 640 - 20 = 620
左右间距 gap = 10
左栏 = (620 - 10) // 2 = 305
右栏 = 305
```

## 三、上半 · 左栏（连接状态）

按"一眼看到最要紧的事"排序，从最重要的往下排：

| 行 | 内容 | 数据源 | 视觉 |
|---|---|---|---|
| 1 | **状态圆点 + 大字** | `net.state` | ● 已连接（绿） / ○ 等待连接（灰） / ● 传输中（蓝） |
| 2 | 本机 IP | `st['ip']` | 等宽感，方便念给对面听 |
| 3 | 对端 IP | `net.peer` | 未连接显示「—」 |
| 4 | 权限 | `st['writable']` | `RW 可写`（黄） / `RO 只读`（蓝） |
| 5 | 卡根 | `st['base']` | 超长省略中间 |
| 6 | 收发累计 | `st['sent']` / `st['recv']` | `↑ 12.3MB  ↓ 4.5MB` |

**为什么第 1 行用圆点 + 大字**：掌机屏幕小、常放在桌上斜看。
"连没连上"是最高频的问题，必须做到扫一眼就知道，不需要读字。

**为什么卡根要显示**：用户从 PC 端看到的路径和掌机上的路径是两回事，
把卡根写出来能立刻消除"我文件传哪去了"的疑问。

### 数据可得性核对

| 字段 | 来源 | 是否已有 |
|---|---|---|
| `net.state` | `NetThread.state`（"idle"/"connected"） | ✅ 已有 |
| `net.peer` | `NetThread.peer` | ✅ 已有 |
| `st['ip']` / `st['port']` | 状态字典 | ✅ 已有 |
| `st['writable']` | 状态字典 | ✅ 已有 |
| `st['base']` | 状态字典 | ✅ 已有 |
| `st['sent']` / `st['recv']` | `xfer_done` 事件累加 | ✅ 已有 |

**结论：左栏不需要任何新的数据管道，全是现成的。** 这是这套方案改动量小的关键。

## 四、上半 · 右栏（关键操作日志）

### 复用而非新建

共享 `app.log_lines`（现为 500 行环形缓冲），首页做**筛选**：

```python
KEY_PATTERNS = (
    "已连接", "已断开", "发现", "自动扫描",
    "待确认", "已允许", "已拒绝", "拒绝",
    "完成", "失败", "异常", "错误",
    "新建目录", "已删除", "中断",
)
```

命中即算"关键"。这样：

- **不新增状态** —— 两个页面读同一个列表，不可能不一致
- **日志页不动** —— 它仍然显示全部，是"详细视图"
- 形成**摘要 ↔ 详情**的自然层次

### 显示规则

- 只显示**最近 N 条**（`N = 可视行数`），最新的在**底部**
  （符合日志直觉：往下是新内容）
- 默认自动定位到最新；用户按上/下滚动后停止跟随
- 行内超长按像素宽度省略（复用现有 `ellipsize`）
- 每条前面带上原有的 `[HH:MM:SS]` 时间戳（`log_lines` 里已含）

### 交互

| 按键 | 行为 |
|---|---|
| `上` / `下` 摇杆 | 向上/向下滚动（滚到底部即恢复"跟随最新"） |
| `A` | 跳到「日志」页看全部 |
| `X` | 打开日志文件（与日志页同功能，复用 `open_log_file()`） |

**为什么 `A` 是"看全部"而不是"清空"**：清空是破坏性操作，
不该出现在首页。看全部是自然的"下钻"动作。

## 五、下半（按键说明）

### 数据源：单一事实来源

现状问题：按键说明**散落两处** —— `_footer_hint()` 里一段字符串，
各 `Page.handle()` 里各有一份实现。两者可能漂移。

**方案**：建一张声明式的按键表，底部说明栏和首页都从它读。

```python
# 每页的按键说明：(键, 说明)
KEY_HELP = {
    "home": [
        ("摇杆上下", "滚动日志"),
        ("A", "查看完整日志"),
        ("X", "打开日志文件"),
        ("L2 / R2", "切换页面"),
        ("SELECT", "锁定 / 解锁"),
        ("START", "退出程序"),
    ],
    "browser": [
        ("摇杆上下", "选择文件"),
        ("A", "进入文件夹 / 查看文件"),
        ("B", "返回上级目录"),
        ("Y", "刷新列表"),
        ("L1 / R1", "翻页（±5 项）"),
        ("SELECT", "锁定 / 解锁"),
        ("START", "退出程序"),
    ],
    "net": [...],
    "log": [...],
    "status": [...],
}
```

### 版面

158px 高度，两列排布，每列约 300px 宽，每列能放 **5~6 行**：

```
┌──────────────────────────┬──────────────────────────┐
│ 🔵  A      进入文件夹     │ ⬆⬇  摇杆   上下选择      │
│ 🔴  B      返回上级       │ 🟡  Y      刷新列表       │
│      L1/R1  翻页 ±5       │      L2/R2  切换页面      │
│      SELECT 锁定/解锁     │      START  退出程序      │
└──────────────────────────┴──────────────────────────┘
```

**配合方案②（动态）**：切到"文件"页时，首页的按键说明不会变
（首页有自己的说明）；但**底栏提示**继续随当前页变。

> ⚠️ 这里有个需要你确认的细节：方案②说的是"随当前页动态变化"。
> 如果首页是独立页，那首页显示的应该是**首页自己的按键**。
> 有两种理解，我倾向前者，见第九节「待确认问题」。

### 按键配色

沿用现有的按键色（`A` 蓝 / `B` 红 / `Y` 黄 / `X` 紫），
**与实机按键颜色一致**，用户不用记"哪个是 A"。

## 八、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **① 内容溢出** | 小屏上文字很容易放不下 | 所有文本走 `ellipsize()`；按键表按「能放几行画几行」自适应，不硬编码 |
| **② `log_lines` 为空时** | 开机初期没有任何日志 | 显示占位提示「暂无记录」，不留空白框 |
| **③ 筛选后可能为空** | 500 行日志里一条关键项都没有 | 退化为显示最近 3 条（不加筛选），保证框里永远有东西 |
| **④ 5 个标签太挤** | 640 宽 ÷ 5 = 124px | 实测够放 2 字；若不行则标签栏字号降一档（`small` 而非 `body`） |
| **⑤ 按键表与实现漂移** | 以后改了某页按键忘了改表 | 加**自动化测试**断言 `KEY_HELP` 覆盖所有页 + 每个页的键都在表里 |
| **⑥ 性能** | 每帧重算筛选 | 筛选结果缓存，只在 `log_lines` 长度变化时重算 |

### 关于风险 ⑤ —— 这是唯一需要写测试的地方

现有的 `test-ui-structure.py` 里可以加一节：

```python
# 8. 首页（第四/五轮反馈）
check("首页已在 PAGE_ORDER 里", "home" in pcmain.PAGE_ORDER)
check("PAGE_LABEL 有首页", ...)
check("KEY_HELP 覆盖所有页面", set(KEY_HELP) >= set(PAGE_ORDER))
# ★ 关键：每个页面 handle() 里认的键，必须在 KEY_HELP 里声明
```

最后一条是**防漂移的核心**：从源码里提取各 `handle()` 判断过的键名，
和 `KEY_HELP` 比对。这能防止"改了代码忘了改说明"这类问题
—— 正是这类"界面说明与实际行为不一致"的问题，在本项目已经
出过一次严重事故（第四轮的确认框焦点 bug）。

## 九、待确认问题

规划里有两处我拿不准，需要你定：

### Q1：首页的按键说明，显示"谁的"按键？

你说的"下面这一半显示掌机端怎么操作"，有两种理解：

- **(a) 显示首页自己的按键**（摇杆滚动日志 / A 看全部日志 / X 打开日志文件 …）
  —— 与"随当前页动态变化"字面一致
- **(b) 始终显示"全局 + 当前标签页"的按键**（不管你在哪一页，
  首页下半总是告诉你怎么操作**其他页面**）

我倾向 **(a)**：首页自己是页面，(a) 语义更自洽，
而且底栏本来就在随页显示提示，(a) 不会和它重复。

### Q2：左栏那 6 项，够不够 / 多不多？

你之前说"还没想好展示什么"。我按"连接状态为主"挑了 6 项
（状态/IP/对端/权限/卡根/收发）。可能你实际用起来会想：
- 加 FPS / 后端 / 固件的**设备信息**？
- 加**当前浏览路径**（PC 端正在看掌机哪个目录）？

这个建议**先按 6 项做出来，你上手看实物再增减** —— 比现在纸上争论有效。
