## 二点五、关于 exe 与 .bat 的三个坑
### 坑 1：`.bat` 里的中文会乱码（用户实测踩到）

**现象**：双击 `启动.bat`，cmd 窗口里一串乱码，
`'C' 不是内部或外部命令`、`'Python' 不是内部或外部命令` 之类。

**根因**：文件用 UTF-8 编码存，而中文 Windows 的 `cmd.exe`
默认按 **GBK** 解析 `.bat`。UTF-8 的中文被逐字节读成乱码，
连 `REM` 注释行都被读坏，导致整段命令错乱。

**修法**（如果确实要用 bat）：
```python
# 必须 GBK + CRLF
open("启动.bat", "wb").write(text.replace("\n", "\r\n").encode("gbk"))
```

**但更好的做法是不要 bat** —— 直接打成 exe，从根上绕开编码问题。

### 坑 2：★★ 打包用的 Python 可能**不含 tkinter**（用户实测踩到）

**现象**：双击 exe 弹出
`ModuleNotFoundError: No module named 'tkinter'`。

**根因**：某些"精简版" Python **不包含 Tcl/Tk**。
本项目开发环境里的隔离 Python（`~/.workbuddy/binaries/...`）就是这种，
而系统装的官方 Python 才有。

**最阴险的地方**：用缺 tkinter 的解释器打包，**打包过程零报错**、
提示"打包成功"，直到用户双击才发现。

**修法**：打包前**实际探一次**，绝不只看版本号。

```python
def has_tkinter(py):
    r = subprocess.run(
        [py, "-c", "import tkinter;print(tkinter.TkVersion)"],
        capture_output=True, text=True, timeout=20)
    return r.returncode == 0, (r.stdout or r.stderr or "").strip()
```

`tools/build-exe.py` 会自动遍历候选解释器（当前环境 → 系统安装 → PATH），
挑第一个 tkinter 可用的。

**顺带一个坑**：候选排序**不能用路径字符串比较** ——
`"Python39" > "Python314" > "Python311"`，
字符串比较会把最老的 3.9 排最前。必须解析成版本号数值再比。

### 坑 3：打成 exe 后，`__file__` 指向的不是程序位置

PyInstaller `--onefile` 运行时会把内容解压到临时目录（`sys._MEIPASS`），
`__file__` 指向那里，**不是 exe 所在目录**。所以
"日志写到 exe 旁边"、"读取同目录的配置文件"这类需求
写 `__file__` 会全错。

```python
def _base_dir():
    """程序所在目录（exe 模式取 exe 的位置）"""
    if getattr(sys, "frozen", False):
        return os.path.dirname(sys.executable)   # ★ 用 executable
    return os.path.dirname(os.path.abspath(__file__))
```

另外 `--windowed` 模式下**没有控制台**，程序崩溃会"静默消失"，
必须自己兜底弹窗 + 写日志：

```python
if __name__ == "__main__":
    try:
        sys.exit(main())
    except Exception:
        tb = traceback.format_exc()
        tkinter.messagebox.showerror(APP, f"程序异常退出：\n{tb[-1200:]}")
        open(os.path.join(_base_dir(), "PocketTransfer-error.log"), "a",
             encoding="utf-8").write(tb)
        sys.exit(1)
```

> 这个兜底这次帮了大忙：正因为有它，用户看到的才是一句明确的
> `No module named 'tkinter'`，而不是"双击没反应"。

这一轮用户真机上跑了一遍，提了 5 个问题。逐个记录原因与修法。

### 问题 1：本机/掌机两栏位置要换

**用户原话**：「本机（windows）这个选择框，应该在左边，和掌机选择框换一下位置」

**改动**：左栏 = 本机 (Windows)，右栏 = 掌机 (RG35XX Pro)。
中间按钮的箭头方向也跟着反过来，**箭头指向 = 文件流向**。

### 问题 2：不能选不同的硬盘

**用户原话**：「不能从这个大选择框里选不同的硬盘？」

**根因**：原来只有一个"选目录"按钮，要从 `C:\` 一路点进 `D:\` 得点很多层。

**改动**：本机栏加盘符下拉框，一步切盘。下拉里同时含：
- 各盘符（`💽 C:` `💽 D:` `💽 F:`，用 `GetLogicalDrives` 枚举）
- 常用目录（`📁 桌面` `📁 下载` `📁 文档`…）

### 问题 3：上传/下载按钮理解不清

**用户原话**：「上传下载两个按钮，怎么理解都不太对，建议改成发送至掌机、发送至电脑」

**改动**：文案改为「← 发送至电脑」「发送至掌机 →」。
"上传/下载"是站在服务器视角的词，对普通用户不直观；
"发送至 X"是动作 + 目标，看一眼就懂。

### ★★ 问题 4：传完一个文件，连接就断了

**用户原话**：「我试着传了个文件，一个 pdf，传过去了，电脑与掌机的连接就断开了，这不行」

**根因（真凶）**：掌机 `net.py` 的 `_handle_tcp_accept` 里有这么一行：

```python
conn.settimeout(20.0)      # 单次读超时，防止半开连接永久占线
```

这个超时**作用于整条连接的每一次 recv**。用户传完文件、去盘里翻下一个，
只要**超过 20 秒**没动作，下一次 `recv_msg()` 就 `socket.timeout`
→ 主循环 `break` → 连接被拆掉。用户看到的正是"传完就断"。

**修法（两半，缺一不可）**：

*掌机侧* —— 把"空闲"和"传输中"两种超时分开：
```python
IDLE_TIMEOUT = 600.0        # 空闲：用户可能在思考/翻文件，要耐心
TRANSFER_TIMEOUT = 30.0     # 传输中：每块之间不该有长间隔，要严格
```
并在 `_serve` 里用 `_set_timeout()` 在两种态之间切换。
另外开 TCP keepalive 兜底（`SO_KEEPALIVE` + `TCP_KEEPIDLE`）。

*PC 侧* —— 加心跳保活，每 25 秒发一次 PING：
```python
def keepalive(self):
    self._send(OP_PING, b"ka")
    self._recv_until({OP_PONG}, timeout=10.0)
    return True
```
UI 层用 `_heartbeat()` 定时器驱动。

> **为什么两半都要**：只改掌机（放宽超时）——网络设备静默丢链时
> PC 侧不知道，用户以为还连着；只加 PC 心跳——万一心跳线程卡住，
> 掌机仍会用短超时误杀。两个一起才是稳的。

### ★ 问题 5：掌机要人按键时，PC 端要有提示

**用户原话**：「需要掌机端手动解锁或者确认的时候，win11 端应该有提示，
提示操作者去掌机上解锁」

**根因**：上传/新建目录时掌机会弹确认框并阻塞 60 秒。
PC 端此时只是干等 `OP_ACK`，UI 上进度条卡住不动 —— 用户完全不知道
要去掌机上按一下，体验上像"卡死"。

**修法**：协议新增 `OP_NOTICE`（掌机 → PC 的单向临时通知）：

```
掌机弹确认框之前，先发：
    OP_NOTICE {kind:"confirm", action, name, size, timeout:60,
               hint:"请在掌机上按 A 允许 / 按 B 拒绝"}
掌机发现只读时，先发：
    OP_NOTICE {kind:"locked", hint:"请按 SELECT 解锁"}
然后再发真正的 ACK / NAK。
```

PC 端 `Client.on_notice` 是回调挂点，UI 层接到后在顶部弹一条**醒目提示条**：
```
⏳  请在掌机上确认：写入文件 xxx.pdf
    按【A】允许，按【B】拒绝（最长 60 秒）
```

这样用户一眼就知道"轮到掌机操作了"，而不是盯着卡住的进度条。

## 二点七、用户实测反馈第三轮（2026-10-05 深夜）

用户又跑了一遍真机，再提 5 条。这一轮里有**两个真正的 bug**（#2），
其余是行为调整。

### 反馈 1：不再要求默认只读

**用户原话**：「不再要求默认只读，也就是往里写文件不再需要先按 select 解锁」

**改动**：掌机启动时 `writable = True`。

```python
# handheld/main.py
"writable": True,                              # 状态字典初值
nt.send_command({"act": "writable", "on": True})  # 启动即同步给网络线程
```

**安全有没有变松？** 没有。真正的把关一直是三道，且全在掌机侧：

1. **路径校验** —— `safe_join()` + `realpath`，越界一律 `NAK_DENIED`
2. **逐次确认** —— 每次写入前掌机屏幕弹框，用户按 A 才落地
3. **受限根目录** —— 只能动卡根以内的东西

这次去掉的只是"还要额外按一次 SELECT"这层**手续**。
SELECT 键仍然有效，语义从"解锁"变成"临时上锁"：
`RW（默认） → 按一下 → RO → 再按一下 → RW`。
用户想临时挡住写入，随时可用。相关文案也统一改成了
「锁定/解锁」而不是「解锁」。

### ★★ 反馈 2：按了 SELECT 解锁后，两端的连接会断开

**用户原话**：「现在按了 select 解锁后，两端的连接会断开」

这条是这一轮最硬的 bug。查下来是**两个独立的根因叠在一起**，
而且都非常隐蔽 —— 单线程测不出来，本机也复现不了。

#### 根因 ①　三个后台线程抢一条 socket（PC 端）

协议是**一问一答式**的：发一个请求，读若干条消息直到拿到应答。
旧版 `Client` 没做任何串行化，于是这条路径炸了：

```
用户传完一个文件 → UI 里 self.busy = False
    ↓ 下一瞬间，三个后台线程同时扑上来
    ① remote_reload()  → LIST_DIR
    ② _refresh_info()  → GET_DEVICE_INFO
    ③ _heartbeat()     → PING
    ↓ 三个线程在同一 socket 上 _send + _recv
    A 线程在等 DIR_LISTING，却把 B 线程要的 DEVICE_INFO 读走了
    ↓ 双方永久卡死 → 掌机侧 keepalive 探到死链
    ↓ [net] 连接结束: [Errno 104] Connection reset by peer
```

用户体感就是"按 SELECT 之后连接断了"—— 因为按 SELECT 的时机，
恰好就是刚传完文件、三个线程正要扑上来的那一刻。

**掌机 `boot.log` 里的铁证**：
```
[08:44:52] [net] 接收完成 对账单.pdf 78.1KB
[08:44:52] [net] LIST PDF → 2 项
[08:44:52] [net] 连接结束: [Errno 104] Connection reset by peer   ← 同一秒！
```

**修法**：给 `Client` 加一把 `threading.RLock`，所有公开 API 整段加锁。

```python
self._io_lock = threading.RLock()   # RLock：download 内部会重入

def list_dir(self, path=""):
    with self._io_lock:
        ...
```

`keepalive()` 特殊处理 —— 用**非阻塞**拿锁，拿不到就跳过这次心跳：

```python
if not self._io_lock.acquire(blocking=False):
    return True      # 此刻有传输在跑，心跳迟到几秒无所谓，插队才有害
```

> **怎么证明修好了**：`test-loopback.py` 第 11b 节用 10 个线程
> 同时打一条连接。**把锁换成假锁（不互斥）后，10 个请求失败 6 个**，
> 报 `magic 不匹配: 0x7322`（正是应答串台的症状）；
> 换回真锁，0 失败。这个测试不是假绿的。

#### 根因 ②　`_stop` 遮蔽了 `Thread._stop()`（掌机端）

掌机退出时 `boot.log` 里总留这么一行，之前一直没深究：

```
停止网络线程异常: 'Event' object is not callable
```

**根因**：`NetThread` 里写了

```python
self._stop = threading.Event()      # ← 灾难
```

而 `threading.Thread` **内部有个私有方法就叫 `_stop()`**，
`join()` 收尾时会调它：

```python
# CPython Lib/threading.py
def _wait_for_tstate_lock(self, block=True, timeout=-1):
    lock = self._tstate_lock
    if lock is None:
        assert self._is_stopped
    elif lock.acquire(block, timeout):
        lock.release()
        self._stop()                # ← 调到的是我们的 Event 对象
```

于是 `net.join(timeout=2.0)` 走到最后一步直接
`TypeError: 'Event' object is not callable`。

> **为什么本地怎么测都不复现**：那条分支只在**线程真的 start 过**
> 之后才走。本地单测经常是构造完对象直接 `join`，压根没 `start()`，
> 于是 `_tstate_lock is None`，走另一条路，永远看不到这个错误。
> 在掌机上用 `python3 -c` 真跑一次 start→stop→join，立刻复现。

**修法**：改名，把 `_stop` 这个**名字还给 CPython**。

```python
# ★★ 千万不要把属性命名为 `_stop`
self._stop_evt = threading.Event()
```

顺带在 `main.py` 的退出收尾里再兜一层 —— 就算 `join` 出问题，
也绝不能阻断退出（否则 UI 卡在退出画面，用户以为死机）：

```python
try:
    net.join(timeout=2.0)
except Exception as je:
    boot.checkpoint(f"net.join 异常（不阻断退出）: {je}")
```

### 反馈 3：PC 端启动自动扫描，5 遍策略

**用户原话**：「pc 端打开就默认扫描，连扫 3 遍后如果还没有连接，
就再扫第 4、5 遍，3/4/5 遍之间每次扫描间隔 20 秒，扫完 5 遍就不再主动扫描了」

**实现**：一个状态机（`_auto_scan_tick` / `_auto_scan_next`）。

| 遍数 | 与上一遍的间隔 | 理由 |
|---|---|---|
| 第 1 遍 | —— | 打开软件时用户和掌机多半就位了 |
| 第 2 遍 | 0.25 秒 | 快速连扫，抓 UDP 应答丢包 |
| 第 3 遍 | 0.25 秒 | 同上；前 3 遍是"快速连扫" |
| 第 4 遍 | **20 秒** | 给用户留出"去把掌机点开"的时间 |
| 第 5 遍 | **20 秒** | 最后一次机会 |
| 之后 | 停止 | 只留一行日志，告诉用户可手点「扫描」 |

扫满 5 遍的日志：
```
已扫满 5 遍仍未找到掌机，自动扫描结束。
  → 请检查：① 掌机已开机 ② 同一个 WiFi ③ 掌机上 PocketTransfer 已点开
  → 就绪后点右上角「扫描」或「连接」重试
```

**手动「扫描」不受 5 遍限制** —— 那 5 遍是给自动扫描用的。
用户主动点，说明就是想再试一次，没道理拦着。

顺带把 `self.cli` 的读写都用 `cli_lock` 保护起来了 ——
自动扫描的后台线程和 UI 线程都会碰它，这是根因 ① 的同类隐患。

### 反馈 4：按钮文案改成「复制进」

**用户原话**：「发送至掌机、发送至电脑，改为复制进掌机，复制进电脑」

**改动**：`← 复制进电脑` / `复制进掌机 →`（宽度 12 → 13）。

上一轮从"上传/下载"改成了"发送至"，这一轮进一步改成"复制进"。
"复制"比"发送"更准 —— 两边都是真文件，说"复制过去"最自然。
箭头方向依然 = 文件流向。

### 反馈 5：文件列表改成四列

**用户原话**：「优化一下 pc 端 2 个大框里面的显示，现在是名称、大小、
修改时间 3 列，改成名称、后缀、大小、修改时间 4 列。

## 二点八、用户实测反馈第四轮（2026-10-05）

这一轮的 #1 是**最危险的一个 bug**：它不是"不好用"，而是
"按了确认键，实际执行的是相反的操作"。在删除、写入这类
不可逆动作上，这种 bug 会直接毁数据。

### ★★★ 反馈 1：确认框语义颠倒 —— 按 A 实际执行了拒绝

**用户原话**：
> 「左边按钮 拒绝（B），右边按钮 允许（A），我看你写的操作逻辑应该是，
> 默认焦点在拒绝按钮上，得手动把焦点移到允许按钮上，再按 A 键，才是允许，
> 直接按 A 键，相当于选择了拒绝，实际上实现的是拒绝功能。
> 这个我觉得得改改，这里改成不需要选择焦点，直接按 B 是拒绝，按 A 是允许。」

**根因**：旧实现是一个"焦点模型"：

```python
# 旧代码（错误）
if n in ("A", "START"):
    c.answer(c.picked == 1)      # ← A 是"确认当前焦点"
```

而 `Confirm.picked` 默认是 `0`（拒绝）。于是：

```
用户想允许 → 按 A → A 确认的是"当前焦点" → 当前焦点是拒绝 → 执行拒绝
```

**语义与直觉完全相反**，而且**用户无法从界面上看出这一点** ——
按钮画得清清楚楚写着"允许（A）"，但按下去是拒绝。

**修复**：改成**直接动作键**，彻底取消"焦点"这个概念对结果的影响。

| 按键 | 结果 | 说明 |
|---|---|---|
| `A` | **允许**（无条件） | 不看任何高亮/焦点状态 |
| `B` | **拒绝**（无条件） | |
| `START` / `MENUF` | **拒绝** | 当作"取消/退出"处理，语义上等于拒绝 |
| `左` / `右` / 摇杆 | 只移动高亮 | **纯视觉**，不影响按 A/B 的结果 |

`picked` 从"决定结果的焦点"降级为"仅表达高亮的展示位置"，
默认值改为 `1`（高亮允许）—— 因为弹这个框说明用户在 PC 上
已经明确表达过"我要做这件事"的意图，掌机这侧是二次确认。

**UI 同步改动**（同样重要 —— 光改逻辑不改界面，用户还是看不懂）：

1. 按钮文案直接写成「**按 B 拒绝**」/「**按 A 允许**」，
   而不是只写「拒绝(B)」/「允许(A)」让用户自己推
2. 去掉旧版那个暗示"先选中再确认"的选中框 ——
   **那正是误导的视觉来源**
3. 补一行提示：「按 A 允许 / 按 B 拒绝（无需先移动选择）」
4. 底部帮助栏从 `←→ 选择   A 允许   B 拒绝` 改成 `A 允许   B 拒绝`

**为什么这个 bug 值得单独写一节**：它说明"界面文案"和
"实际语义"必须由同一套模型派生。旧版 UI 上写的是"允许(A)"，
代码里的模型却是"焦点式选择" —— 两者对不上，bug 就藏在这个缝里。
教训是：**不要在一个按钮上同时表达"选项"和"动作"两种语义**。

专项测试：`tools/test-confirm-keys.py`（30 项）。其中最关键的三条：

```
★★ 默认状态下按 A → 允许（旧版这里会变成拒绝）
★★ 高亮在「拒绝」时按 A，结果仍是允许（A 不做焦点确认）
★★ 高亮在「允许」时按 B，结果仍是拒绝
```

### 反馈 2：自动扫描改成"7 秒一次，5 分钟后停"

**用户原话**：
> 「改成 win11 端启动后进行一次扫描，然后每隔 7 秒进行一次扫描，
> 直到启动软件 5 分钟后停止自动扫描。」

第三轮定的是"5 遍 + 第 3 遍后间隔 20 秒"，用户实测觉得不合适。
本轮换成**时间窗模型**（比数遍数更直观，也更好解释给用户）：

```python
AUTO_SCAN_INTERVAL_S = 7.0      # 每拍间隔
AUTO_SCAN_WINDOW_S = 300.0      # 总时间窗（5 分钟）

def _auto_scan_start(self):
    self._scan_t0 = time.time()     # ★ 记下起点
    self.scan_round = 0
    self._auto_scan_tick()

def _auto_scan_tick(self):
    # ★ 到点就停：判据是"距启动的秒数"，不是扫了多少遍
    elapsed = time.time() - getattr(self, "_scan_t0", time.time())
    if elapsed >= self.AUTO_SCAN_WINDOW_S:
        self._stop_auto_scan()
        ...
```

停止时不只是静默停下，会给一段可执行的排查建议
（掌机开机了吗 / 同一个 WiFi 吗 / 掌机上应用点开了吗）。

`do_scan()`（手动扫描）不受这个 5 分钟限制 —— 自动扫描是"帮你找"，
手动点是"我现在就要找"。

### 反馈 3：新建目录按钮文案

**用户原话**：
> 「新建目录按钮，应为在掌机当前目录下新建目录，修改名称。」

按钮文案：`新建目录` → **`在掌机当前目录\n新建文件夹`**

弹窗里也带上完整的掌机目标路径：

```
在【掌机】的当前目录下新建文件夹

掌机位置：/Roms/GBA

请输入文件夹名称：
```

**为什么要连弹窗一起改**：按钮上写清楚只是第一步。
用户点进去之后，如果弹窗只说"请输入文件夹名称"，
他还是不确定这个目录会建在哪里 —— 尤其这个软件两边都在
浏览文件系统，"当前目录"是有歧义的。把路径写进弹窗才真正闭合。

### ★ 反馈 4：新增删除按钮（双端确认）

**用户原话**：
> 「在新建目录按钮下面，新增一个"删除当前选中的掌机文件"按钮，
> 当有掌机文件被选中时，该按钮可用。需要双端确认，
> 电脑端出一个弹窗确认，掌机端也要有个确认弹窗，
> 样式可以和写入确认弹窗一致」

**按钮可用性规则**（`_on_remote_select`）：

| 状态 | 按钮 |
|---|---|
| 没选中任何掌机项 | 禁用 |
| 选中了掌机文件，且空闲 | **可用** |
| 正在传输（busy） | 禁用（一律） |

注意第三条：`_enable()` 在忙碌时会禁用一整组按钮，
`_on_remote_select` 必须**尊重 busy 状态**，
不能在传输过程中把删除按钮点开。

**双端确认链路**（这是本轮新增的协议）：

```
PC: messagebox.askokcancel(default="cancel")     ← 第 ① 道（PC 端弹窗）
  │   内容：文件名 / 大小 / 位置 + "⚠ 删除后无法恢复"
  ↓  用户点"确定"
PC → 掌机: OP_DELETE_BEGIN(0x0031) {path}
  │
掌机: _request_confirm("delete", ...)             ← 第 ② 道（掌机弹框）
  │   ★ 与写入确认**同一个** Confirm 类 → 样式自动一致
  │   ★ 框上明确写"★ 此操作不可恢复"
  ↓  用户按 A
掌机 → PC: ACK
```

任一道拒绝都不删。用户在掌机上按 B → `NAK_NO_CONFIRM(2)`，
**文件必须原封不动** —— 这条是回环测试里最关键的一条断言
（`★★ 拒绝后文件依然存在`）。

**几个设计细节**：

* **删除不需要 `is_writable()` 解锁**。这是"操作手续"不是"安全边界"，
  用户在掌机上按 A 才是真正的最终授权（与第三轮去掉默认只读同一逻辑）。
* **删目录单独拦一道**，返回 `NAK_IS_DIR(6)`。删目录涉及递归，
  风险面比删文件大得多，这一版不做，给一个能直接展示给人看的原因码，
  而不是让它失败在一个模糊的错误里。
* **PC 端 `delete()` 超时给 75 秒**（掌机确认窗是 60 秒）。
  给少了 PC 会先超时断开，而用户其实还在掌机上看那个框 ——
  体验上就是"莫名其妙断连"。
* **PC 端只选了目录时给明确提示**，而不是静默跳过。

## 二点十、用户实测反馈第六轮（2026-10-05）：三个 bug

### #1 掌机按 SELECT 切读写，PC 端不跟着变（★ 状态同步）

用户原话：
> "按下 select 键，win11 端这里能检测到，右上角也有相应提示，
> 但是再按一下 select 键，win11 这边就没有同步状态。"

**根因（两个叠加）**：

1. 掌机 `set_writable()` 只改本地标志，**从不通知对端** ——
   PC 只在连接握手时读过一次 writable，之后再也没人告诉它变了。
2. 就算掌机想推通知，PC 端的通知回调只在"自己正在等应答"时才会被触发；
   用户切完 SELECT 后 PC 是空闲的，正阻塞在自己的心跳等待里，
   通知到了也没人读。

**修法（两头一起动，缺一不可）**：

* 掌机：`set_writable()` 状态真的变化时，往命令队列塞一条
  `notify` 命令；`_serve` 主循环从"阻塞等包"改成 **0.5 秒轮询**，
  每轮先排空命令队列把通知发出去。状态没变时不重复推（防刷屏）。
* PC：心跳间隔 25 秒 → **4 秒**（刻意比人连按两下 SELECT 的间隔短），
  且心跳从 `PING` 改成 **`GET_DEVICE_INFO`** —— 一次往返同时完成
  "保活"和"把最新 writable 带回来"，作为通知丢失时的兜底通道。
  收到后 `_apply_perm()` 在主线程刷新权限标签。

**测试**：`test-loopback.py` 新增 11c 节（61 项），
专门回归"切过去能收到、再切回来也能收到"——用户卡住的就是第二步。

### #2 掌机 IP 不能写死默认值（★ 配置记忆）

用户原话：
> "分享给别人用就不一定是什么 ip 了……连接成功一次后，后面就默认是这个，
> 如果后面又在别的 ip 连接成功了，就再换成新的 ip。"

* 删除硬编码的 `DEFAULT_HOST = "192.168.3.25"`。
* 启动时按 **「命令行 --host > 配置里上次连成功的 > 留空」** 取值。
* 留空时输入框是一段**灰色占位提示**（"点「扫描」自动发现，或填掌机 IP"）。
  实现上占位文字是一个浮在输入框上的独立 Label，
  **绝不写进 `var_host`** —— 否则用户直接点「连接」会拿占位文字去连。
* 连接成功 → 写 `%APPDATA%\PocketTransfer\config.json` 的 `last_host`
  （`os.replace` 原子替换，写失败静默 —— 记不住 IP 不该影响使用）。
  在别的 IP 上又连成功就覆盖，永远记"最近一次成功的"。
* 版本号升到 **v0.3**。

### #3 本机栏默认目录改成桌面

用户原话：
> "左边默认打开的目录设置成桌面路径，默认大概 c 盘目录的话普通人会懵逼。"

* 新增 `default_local_dir()`：依次找 `~/Desktop`、`~/桌面`，
  都没有（极少见）才退回用户主目录。
* 下拉框里本来就有"桌面"快速位置项，启动后会自动同步选中它。

### 附带逮到的回归：NOTICE 夹在应答之间

给 `set_writable()` 加了主动通知后，`tools/test-stage2.py` 当场有 6 项失败：
上传结束后测试用裸 `recv()` 等最终 ACK，读到的却是**夹在中间的
NOTICE(perm)**（0x0042）。真实 PC 客户端不受影响
（它走 `_recv_until()`，NOTICE 转给回调后继续等真正应答），
是测试脚本自己没用对等的语义。已改为 `recv_final()`。
**教训：协议里新增一种"随时可能插进来"的消息后，
所有裸 `recv()` 的测试脚本都要重新过一遍。**

## 三、协议速查

### 包格式

```
┌─────────┬────────┬──────────┬─────────────┐
│ MAGIC   │ OP     │ LENGTH   │ PAYLOAD     │
│ 2 字节  │ 2 字节 │ 4 字节   │ LENGTH 字节 │
│ 0x504B  │ 大端   │ 大端 u32 │             │
└─────────┴────────┴──────────┴─────────────┘
```

同一台机器上：TCP `48200`（数据）、UDP `48211`（发现广播）。

### 操作码表

| 码 | 名称 | 方向 | 说明 |
|---|---|---|---|
| 0x0001 | PING | PC→掌机 | 心跳 |
| 0x0002 | PONG | 掌机→PC | 心跳回显 |
| 0x0003 | GET_DEVICE_INFO | PC→掌机 | 取设备信息 |
| 0x0004 | DEVICE_INFO | 掌机→PC | 型号/固件/IP/卡根/权限 |
| 0x0010 | LIST_DIR | PC→掌机 | 列目录 |
| 0x0011 | DIR_LISTING | 掌机→PC | 目录内容（JSON 数组）|
| 0x0012 | GET_FILE | PC→掌机 | 请求下载 |
| 0x0013 | FILE_CHUNK | 掌机→PC | 数据块（4 字节序号 + 数据）|
| 0x0014 | FILE_END | 双向 | 结束宣告 |
| 0x0020 | PUT_FILE_BEGIN | PC→掌机 | 请求上传（★需掌机确认）|
| 0x0021 | PUT_FILE_CHUNK | PC→掌机 | 数据块（4 字节序号 + 数据）|
| 0x0030 | MKDIR_BEGIN | PC→掌机 | 请求建目录（★需掌机确认）|
| 0x0031 | DELETE_BEGIN | PC→掌机 | 请求删文件（★需掌机确认，不可逆）|
| 0x0040 | ACK | 双向 | 确认 |
| 0x0041 | NAK | 双向 | 拒绝（带原因码）|
| 0x0042 | NOTICE | 掌机→PC | 信息性通知（不改变请求/应答流程）|
| 0x00FF | BYE | 双向 | 道别 |

### NOTICE 的 kind（★ 客户端必须逐个处理，见下）

| kind | 什么时候发 | PC 端反应 |
|---|---|---|
| confirm | 弹确认框**之前** | 顶部弹醒目条"请去掌机按 A" |
| locked | 只读时收到写请求 | 顶部弹醒目条"按 SELECT 解锁" |
| busy | 忙碌时收到新请求 | 日志提示稍后重试 |
| **perm**（第六轮新增） | **用户在掌机上按了 SELECT，读写状态变更** | 刷新权限标签 + 日志（🔓/🔒）|

> ★ 第六轮教训：状态变更**必须主动通知**对端，而且通知**必须有人接**。
> 旧版 `set_writable()` 只改本地 bool，PC 永远不知道；
> 而 PC 的通知回调只在自己等应答时才会被触发，空闲时通知没人读。
> 修法是两头一起动：掌机 `_serve` 改 0.5 秒轮询、及时把通知发出去；
> PC 心跳从 25 秒提速到 4 秒、并改用 `GET_DEVICE_INFO`
> （一次往返同时保活 + 把最新 writable 带回来，作为通知丢失时的兜底）。

### NAK 原因码 → 用户看到的话

| 码 | 内部名 | PC 端显示 |
|---|---|---|
| 1 | NAK_LOCKED | 掌机处于只读，请按 SELECT 解锁后重试 |
| 2 | NAK_NO_CONFIRM | 你在掌机上拒绝了本次操作 |
| 3 | NAK_DENIED | 掌机拒绝了该路径（越界或无权限）|
| 4 | NAK_BUSY | 掌机正忙 |
| 5 | NAK_BAD | 请求格式不合法 |
| 6 | NAK_IS_DIR | 目标是文件夹，当前版本只支持删除文件 |

## 四、★ 两个必须记住的协议设计决策

这两条都是**踩过坑之后定下来的**，改动前务必看懂原因。

### 决策 1：数据块必须带 4 字节序号，服务端必须剥掉

```
数据块 payload = [4 字节块序号][原始文件数据]
                 序号 = 该块之前的累计字节数
```

**坑的经过**：最早服务端把整个 payload（含序号）直接写进文件，
于是每 64KB 就混进 4 字节脏数据。文件**大小看着是对的**
（因为客户端上报的是纯数据长度），但 md5 必然不符 ——
这种"看起来成功、实际损坏"的 bug 最危险。
回环测试用 md5 比对当场逮住。

**序号还有什么用**：连续性校验。收到断裂就立刻失败，
而不是继续写一个已经错乱的文件。

### 决策 2：上传收尾由 `OP_FILE_END` 驱动，不在"收满"时抢跑

**坑的经过**：最早服务端在 `_do_put_chunk` 里判断
`if got >= expect: _finish_put() + ACK`。结果客户端紧接着发的
`OP_FILE_END` 落到了主循环，被当成"未知操作 FILE_END"回了一个 NAK。

更糟的是**用户拒绝**场景：客户端嘴还在把 FILE_END 发完，
服务端却已经收场 —— 双方对"会话进行到哪"的认知错位。

**正确做法**：收满只代表"数据到齐"，结束由显式的 FILE_END 宣告。
两边状态机严格对称，谁都不抢跑。

## 五、安全模型（三道门，全在掌机侧）

```
PC 想写文件
    │
    ├─ 门 1：掌机是否已解锁？        ← 掌机上按 SELECT
    │        没解锁 → NAK_LOCKED
    │
    ├─ 门 2：路径是否在卡根内？      ← safe_join + realpath
    │        越界 → NAK_DENIED
    │        （realpath 而非 normpath，软链也一并解析）
    │
    └─ 门 3：用户在掌机上按了 A 吗？ ← 弹确认框，阻塞等 60 秒
             按 B 或超时 → NAK_NO_CONFIRM
```

**这三道门全部在掌机上执行，PC 端无法绕过。** 这是刻意的设计：
掌机是文件的主人，电脑只是访客。

补充说明：
- 路径穿越实测：`../../../etc/passwd` → 原因码 3；
  `/etc/passwd` → 原因码 5（前导 `/` 被剥，落在卡根内但不存在，故判"非法路径"）。
  **两种都安全**，都没跑出卡根。
- 掌机侧**从不**执行 PC 发来的任何命令，只做文件读写。

| 进目录 | 双击目录；「↑ 上级」返回；位置下拉框一键跳盘符/桌面/下载等 |
| 复制到电脑 | 右边（掌机）选中文件 → 点「← 复制进电脑」。存到本机当前目录 |

### 常见问题

**「扫描」找不到掌机**
1. 掌机上 PocketTransfer 必须**正在前台运行**（网络线程在应用里）
2. 确认两边连的是同一个 WiFi
3. 有些路由器开了「AP 隔离」，会挡住广播 —— 那就手填 IP

**上传一直卡住 / 报"用户拒绝"**
掌机屏幕弹了确认框，要按 **A 允许**（按 B 是拒绝；60 秒不理自动算拒绝）。

**写入被拒、提示只读**
在掌机上按 **SELECT** 切换读写状态，PC 端 4 秒内会同步显示 🔓/🔒。
（自第三轮起掌机默认就是可写；SELECT 是随时上锁/解锁的开关。）

**掌机 IP 变了**
直接点「扫描」重找；连上后新 IP 自动记成默认 —— 这正是第六轮 #2 的行为。
想在路由器里绑固定 IP 也行，但不是必须。

## 八、已知限制

| 限制 | 说明 |
|---|---|
| 不支持整目录传输 | 需逐个文件。将来可以加递归 |
| **不支持删除目录** | 返回 `NAK_IS_DIR(6)`。删目录涉及递归，风险面大，本版不做 |

| 无 MD5 校验字段 | 目前靠块序号连续性 + 大小比对；可加 end-to-end 摘要 |
| 删除无回收站 | 掌机上 `os.remove` 直接删，**不可恢复**，所以确认框上明确写了这一点 |

## 十、为什么这些坑值得写下来

这些 bug 有个共同特征：**表面正常，实际错误**。

1. `_put_ctx` 未初始化 —— 平时不崩，一来 PUT 就崩
2. 序号混进数据 —— 文件大小对，内容错
3. 收尾抢跑 —— 最后一个包被当"未知操作"
4. 20 秒空闲超时 —— 传完就断，看着像网络问题，实际是超时设错
5. **确认框焦点语义 —— 界面上写着"允许(A)"，按下去执行的是拒绝**

前四个是"数据/连接"层面的坑，第五个是**"人与界面的契约"**层面的坑：
用户读到的意思和代码执行的意思不一致。这类 bug 更隐蔽，
因为**代码本身没有错**（`c.answer(c.picked == 1)` 逻辑完全正确），
错的是"把 A 键定义成确认焦点"这个**设计选择**。

单靠"点一遍看看"很难发现前四个（第 2 个尤其：传完显示"完成"，
文件也能打开，只是内容悄悄多了几千个 4 字节垃圾）；
第五个更糟 —— 用户点了、界面也响应了、流程也走完了，
**只是结果是反的**，而且往往要到"文件没了"才发现。

**唯一可靠的发现手段是把断言写成可执行的测试。**
所以回环测试里每一处传输都做 md5 校验，
确认框的每一条按键路径都要有断言 —— 这不是形式主义。
