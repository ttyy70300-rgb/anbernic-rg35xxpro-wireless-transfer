## 一句话结论

**掌机端从「C + 裸 framebuffer + 交叉编译」改为「Python + Pillow + 直接 mmap framebuffer」。**

## 为什么改：三个决定性发现

### 发现 1：固件自带完整 Python 桌面应用栈

实测 `/usr/bin/python3 -V` → **Python 3.10.12**，且配套齐全：

| 组件 | 版本 | 位置 |
|---|---|---|
| Python | 3.10.12 | `/usr/bin/python3` |
| pysdl2 | 0.9.17 | `/usr/lib/python3/dist-packages/sdl2/`（含 `ext/`） |
| Pillow | 9.0.1 | 系统包 |
| SDL2（**pysdl2 实际加载**） | **2.28.5** | `/usr/lib/aarch64-linux-gnu/libSDL2-2.0.so.0.2800.5` |
| SDL2（原厂 dmenu 静态链接用） | 2.0.12 | `/usr/lib/libSDL2-2.0.so.0.12.0`（含 `.a` 与头文件） |
| gcc | 11.4.0 aarch64 | `/usr/bin/`（glibc 2.35） |

> ⚠️ **两个 SDL2 并存**（实测 `SDL_GetVersion()` → **2.28.5**）。详见 `docs/固件信息核实.md` §4.2。

用户空间是 **Ubuntu 22.04**（`/etc/os-release` 确认），不是常见传闻的 Buildroot。
**固件是 Anbernic 官方包 `20260522`**（`/mnt/vendor/oem/version.ini` 确认），非第三方魔改。

**关键佐证：原厂 5 个应用全部是 Python 写的**

```
/mnt/mmc/Roms/APPS/
├── 时钟.sh              → clock/{main,app,graphic,input,language,weather}.py
├── 图片浏览器.sh         → img_browser/…
├── 魔改系统工具.sh       → mod_tools/…
├── 魔改系统设置.sh       → mod_set/…
└── 瑞士小刀抓取器.sh     → tiny_scraper/…
```

原厂启动脚本（`时钟.sh`）的全部内容：

```bash
#!/bin/bash
progdir="$(cd $(dirname "$0") || exit; pwd)"/clock
export PYSDL2_DLL_PATH="/usr/lib"
program="python3 ${progdir}/main.py"
log_file="${progdir}/log.txt"
$program > "$log_file" 2>&1
```

这就是官方示范的部署结构与启动方式，v1.2 的部署结构判断完全正确。

**含义**：我们要做的事，原厂已经用 Python 做过一遍。跟着走，风险最低。

### 发现 2：EGL / GPU 路线彻底不通 ~~（此结论已于 2026-10-05 作废，见文末附录）~~

> ⚠️ **本条结论是错的，请直接跳到文末「附录：v1.3 作废结论更正」。**
> 留在此处仅为保留推理链与教训。

想用 SDL2 就得初始化 EGL，而这条路是死的：

```
eglGetDisplay  → 返回非空句柄
eglInitialize  → 返回 0，errno = 0x3008 = EGL_BAD_DISPLAY
```

排查过程与结论：

- GPU 设备节点是 `/dev/mali0`（**不是** `/dev/mali`），`mali_kbase` 模块已加载
- 建软链 `/dev/mali → /dev/mali0`：无效
- 10 余种环境变量（`EGL_PLATFORM=surfaceless/device`、`MESA_DEBUG`、`LIBGL_DEBUG=verbose`、`LD_PRELOAD=libmali.so.1` 等）：全部无效
- SDL2 枚举出的视频驱动只有 `mali / dummy`（`offscreen` 与 `evdev` 在 Init 后不可用），**没有 fbdev**
- **原厂 clock app 在 SSH 里同样失败** —— 证明这条 EGL 路径在本固件上本来就跑不通

而原厂菜单 `dmenu.bin` 的依赖是：

```
libSDL-1.2.so.0   libSDL_image-1.2.so.0   libSDL_ttf-2.0.so.0
libSDL_gfx.so.15  libfreetype.so.6         libpng12.so.0
```

**SDL 1.2 直涂 framebuffer，完全不碰 EGL** —— 所以这个坏掉的 GPU 路径对它无所谓。

**含义**：任何依赖 EGL 的方案（SDL2、pygame、Qt、GTK）在这台机器上都会失败。唯一可靠路径是直接操作 `/dev/fb0`。

### 发现 3：v1.2 假定的显示模式是错的

v1.2 写「640×480，32bpp，red=16 green=8 blue=0」。这个数值**只在 dmenu 尚未启动时成立**。

实测对照：

| 状态 | 分辨率 | 色深 | 通道偏移 | stride |
|---|---|---|---|---|
| dmenu 运行中 | **1280×1024** | **16bpp (RGB565)** | 0/0/0 | 2560 字节 |
| dmenu 未启动（早期误读） | 640×480 | 32bpp | 16/8/0 | 2560 字节 |

两者 stride 相同（`1280×2 = 640×4 = 2560`），说明是**同一块显存**，只是时序与像素打包不同。dmenu 用的 1280×1024 是为 HDMI 兼容准备的虚拟模式。

**教训**：早期那次「fbtest 读到 640×480 32bpp」的探测是在 dmenu 还没起来时做的，属于时序巧合，不是稳定事实。

**含义**：程序必须在运行时读 `fb_var_screeninfo` 决定怎么画，不能硬编码。同时**不要用 `FBIOPUT_VSCREENINFO` 强切模式** —— 实测 PUT 返回 0 且 GET 读回新值，但 sysfs 仍显示旧值，说明显示时序由 disp 驱动独立控制，改 var 只是改了软件视角，反而可能画错位置。

## 技术栈定案

### 掌机端

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | **Python 3.10** | 固件自带，与原厂应用一致 |
| 绘图 | **Pillow 9.0.1** | 文字、列表、图标全靠它 |
| 显示 | **★ SDL2 `SDL_WINDOW_FULLSCREEN_DESKTOP`** | 见 `handheld/sdl_display.py`。**勿用裸 fb0**（会被 disp 图层盖住） |
| 输入 | **裸读 `/dev/input/event1`** | 24 字节 `struct llHHI`，照抄原厂 `input.py`；**摇杆走 EV_ABS** |
| 震动 | **写 `/sys/class/power_supply/axp2202-battery/moto`** | 写 `1` 开 / `0` 关 |
| 服务端 | **`socketserver`（标准库）** | TCP 服务端，协议按 v1.2 不变 |
| 部署 | **APPS 根 `.sh` + 兄弟目录负载** | 原厂契约，v1.2 已正确 |

### 关键实现约束

**framebuffer 写入性能**

`fb.py` 用两条快速路径（均已本地验证）：

- 32bpp BGRA（`red=16 green=8 blue=0`）：逐行 `bytes` 切片重排，约 0.1s/全屏
- 16bpp RGB565（偏移全 0）：逐通道 `bytes.translate` 查表 + 交错，约 0.2s/全屏（x86 实测，掌机约 0.6~1.0s）

另加**变化检测**：与上次上屏内容逐字节比对，无变化直接跳过。UI 只需在状态改变时重绘。

**`fb_var_screeninfo` 结构体布局**（⚠️ 本段原内容**偏移全错**，已于 2026-10-05 修正）

> 原文写「必须包含 `__` 前缀私有头，xres 在偏移 64」—— **这是错的**。
> 实机逐字节 dump 证明是**标准 uapi 布局，无私有头**。错误偏移曾导致
> `bpp` 读到物理高度 94mm、报「不支持的色深 94bpp」，连兜底错误屏都画不出来。
> 详见 `v1.4闪退修复记录.md` 附录。

正确偏移（实机 dump 校准，与 `fb.py` 一致）：

```
fb_var_screeninfo:
  xres=0  yres=4  xres_virtual=8  yres_virtual=12
  xoffset=16  yoffset=20  bits_per_pixel=24  grayscale=28
  red=32  green=44  blue=56  transp=68
  nonstd=80  activate=84  height=88  width=92

fb_fix_screeninfo:
  smem_start=16  smem_len=24  line_length=48
```

`var` = 192 字节，`fix` = 112 字节。**必须用实机 dump 验证，不能靠记忆。**
回归断言见 `tools/selftest.py` 第 6 / 第 10 节。

> 注：走 SDL2 路线后，程序**不再需要自己解析这两个结构体**。
> `fb.py` 保留作为兜底后端，其偏移常量仍需正确。

**ioctl 用 ctypes 而非 fcntl**

`fcntl.ioctl` 的可变 buffer 形式与 `ctypes` 调 libc 读出的数据一致（都受 dmenu 持锁影响），但 ctypes 与 C 程序行为完全一致、更可控，且便于后续 `FBIOPUT_VSCREENINFO`。统一走 ctypes。

### PC 端

**不变**。C# + WPF + .NET 8，自定义 TCP 客户端，协议按 v1.2 执行。

## 原厂启动契约（必须理解）

从 `/mnt/vendor/ctrl/dmenu_ln` 源码读出的完整机制：

```bash
ACT="/tmp/.next"
CMD="/mnt/vendor/bin/dmenu.bin"

app_scheduling() {
    if $CMD > /dev/null 2>&1; then      # 前台运行 dmenu
        if [ -f "$ACT" ]; then          # 用户选中应用后 dmenu 写了 /tmp/.next
            if ! sh $ACT; then ...      # dmenu 已退出，这里执行我们的应用
        fi
    else
        sleep 30                          # dmenu 异常退出，重试
    fi
}
```

外层 `/mnt/vendor/ctrl/loadapp.sh:222`：

```bash
while [ -f $RunBin ]; do
    if [ -f $StopBin ]; then break; fi
    $RunBin
done
```

dmenu.bin 内部字符串印证：`/mnt/mmc/Roms/APPS`、`chmod 777 /tmp/.next`、`Unable to write next command`。

**结论**：
1. 应用退出后，dmenu 会**自动重启**，菜单自然回来 —— 不需要我们做任何清理
2. dmenu 的关闭信号是 **SIGUSR1**（`/etc/init.d/launcher.sh:45`），SIGINT 无效
3. **绝不能反复 kill dmenu** —— 它来不及完成初始化会黑屏

### ⚠️ 操作纪律（血的教训）

**任何自动化脚本都不允许 kill `dmenu` / `dmenu_ln` / `loadapp`。**

本轮曾因反复 kill dmenu 导致掌机黑屏。启动应用一律由用户在掌机上手动点击菜单。

工具现状：

| 工具 | 状态 | 用途 |
|---|---|---|
| `tools/deploy-only.py` | ✅ 启用 | 只上传文件 + 装启动脚本，**不启动** |
| `tools/rr.py` | ✅ 启用 | 通用 SSH 命令执行（避开 Bash 引号问题） |
| `tools/run-native.py` | ⛔ `.DISABLED` | 会 kill dmenu，禁用 |
| `tools/deploy-app.py` | ⛔ `.DISABLED` | 会自动运行，禁用 |

## 为什么错：探测方法有三处硬伤

### 硬伤 1：在 SSH 会话里测 SDL

SSH 会话**没有 TTY、没有 disp 上下文**，EGL 初始化必然失败。
当时正是拿 SSH 里的失败结果，得出了"SDL2 在这台机器上不可用"的错误结论。

**正确做法**：GUI 程序必须**从掌机菜单真实启动路径**上测。
工具 `tools/probe-sdl.py` 就是为此写的（从菜单点进去跑）。

### 硬伤 2：用 `ldd` 看 dmenu 依赖

```
$ ldd /mnt/vendor/bin/dmenu.bin
不是动态可执行文件          ← ldd 什么也看不到
```

dmenu 是**静态链接**的，`ldd` 对它无效。于是误判它"走 SDL1.2 直涂 fb"。

**正确做法**：`strings dmenu.bin | grep -E '/dev/disp|/dev/ion'`

```
/dev/disp
/dev/ion
CdcIonAlloc err, ret %d
CdcIonGetFd map other dev's handle err
CdcIonMmap failed: %s
DisplayEngine Frequency: %ld Hz
```

### 硬伤 3：漏掉了 `/dev/disp` 的存在

没有检查设备节点，完全没意识到这是 **Allwinner DispEngine 多图层合成器**，
而不是单 framebuffer。这是整件事的根因。
