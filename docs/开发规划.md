## 一、项目定位

做一个**图形化**的掌机文件管理工具，替代 SSH / Samba / WinSCP 这类"太专业"的方案，让不懂命令行的用户也能轻松把 PC 上的游戏、存档传到掌机。

### 为什么不用现成方案

| 方案 | 问题 |
|---|---|
| SSH + WinSCP | 需要查 IP、填账号密码、命令行操作，对普通用户门槛过高 |
| Samba 共享 | 客户端配置繁琐，且**掌机侧完全没有确认环节**，误操作无法拦截 |
| 原厂文件管理器 | 功能太弱，无跨设备传输能力 |

### 核心设计原则

1. **掌机掌握最终决定权** —— 任何写操作都必须经掌机侧确认，PC 端无权绕过
2. **轻量** —— 掌机端二进制 < 500KB，启动 < 1 秒，1GB 内存毫无压力
3. **零配置** —— 同一 WiFi 下自动发现，用户不需要知道任何技术细节
4. **可移植** —— 核心逻辑与硬件解耦，便于在 PC 上开发和测试

### ★ 显示层：必须走 SDL2（v1.4 重大发现）

**本机显示子系统是 Allwinner DispEngine 多图层合成器（`/dev/disp`），不是单 framebuffer。**

```
【模型 A：单 framebuffer】—— 多数教程假定
   程序 ──写──> /dev/fb0 ──> 屏幕          （你写什么就显示什么）

【模型 B：多图层合成器（本机 ★）】
   你的程序 ──写──> /dev/fb0        ┐
   别人程序 ──写──> /dev/disp 图层  ┘──> 硬件合成 ──> 屏幕
                     ↑ z-order 决定谁在上面
```

`/dev/fb0` 是**最底层**。原厂菜单 `dmenu.bin` 退出时**不做 `DISP_BLANK` 清理**，
残留的"加载中"画面会**完全盖住**你写在 fb0 上的内容。

**铁证**：把 fb0 整块 7MB 逐页扫一遍，**找不到 dmenu 画的画面**。
`dmenu.bin` 是静态链接，字符串含 `/dev/disp`、`/dev/ion`、`CdcIonAlloc`、`DisplayEngine Frequency`。

**结论**：SDL2 的 `FULLSCREEN_DESKTOP` 会 `open("/dev/disp")` 建**自己的顶层图层**，
退出时销毁 —— 这是唯一能显示出来的路径。原厂 5 个应用全都这么做。

> **→ 完整实现与三个必踩的坑，见 [`RG35XXPro-开发成功经验.md`](RG35XXPro-开发成功经验.md)。**

### 为什么不用 SSH（重要说明）

原厂固件**自带** SSH 和 Samba，但复用它们会导致需求 ①（自动发现）无法实现——SSH 没有发现机制，用户仍需手动查 IP 填入。

更关键的是**架构级约束**：SSH 是单方面主从控制，PC 一连上就拥有 root 权限。而本项目需求 ④ 要求"掌机侧掌握最终决定权"，任何复用 SSH 的方案在架构上都无法实现掌机侧确认。

因此采用自定义协议，但会复用系统已有的成熟能力（socket API 做通信），而非从零造轮子。

> 注意区分两个用途：
> - **产品功能**不用 SSH（架构约束）
> - **开发调试**要用 SSH（推文件 + 读日志，见第十七章）

### 角色划分

**掌机端 = 服务端（Server）**，持有文件和最终决定权。监听 TCP 端口，处理来自 PC 的所有请求。

**PC 端 = 客户端（Client）**，主动连接掌机。所有写操作必须等待掌机端返回确认结果。

**关键设计**：掌机端作为服务端，意味着 PC 无法绕过掌机直接操作文件——这是安全模型的根基。

**v1.2 新增**：卡根（`/mnt/mmc` 或 `/mnt/sdcard`）由启动脚本通过环境变量 `BASE_PATH` 传入，
程序不需要在运行时猜测自己管理哪张卡。这消除了 v1.1 方案中「挂载点探测失败 → 卡槽显示错误」的失败模式。

## 五、通信协议设计

### 5.1 报文格式

固定 4 字节包头 + 变长负载：

```
┌─────────────┬─────────────┬─────────────┬─────────────┐
│ MAGIC (2B)  │ TYPE  (2B)  │ LENGTH (4B) │  PAYLOAD    │
│   0x504B    │  操作码     │  负载字节数  │  变长数据    │
└─────────────┴─────────────┴─────────────┴─────────────┘
```

- **MAGIC**：`0x504B`（"PK"），用于快速丢弃非法包和 TCP 流错位恢复
- **TYPE**：操作码，见下表
- **LENGTH**：网络字节序（大端）的负载长度
- **PAYLOAD**：JSON（文本操作）或二进制块（文件传输）

采用大端序避免跨平台字节序问题。所有整数一律使用固定宽度类型，禁止依赖 C 的 `int`/`long` 宽度。

### 5.2 操作码清单

| 类别 | TYPE | 名称 | 方向 | 说明 |
|---|---|---|---|---|
| 系统 | 0x0001 | `PING` | PC→掌机 | 心跳保活 |
| 系统 | 0x0002 | `PONG` | 掌机→PC | 心跳响应 |
| 系统 | 0x0003 | `GET_DEVICE_INFO` | PC→掌机 | 获取设备名、存储信息、锁定状态 |
| 系统 | 0x0004 | `DEVICE_INFO` | 掌机→PC | 响应 |
| 发现 | 0x0010 | `BEACON` | 掌机→广播 | 每 5s 广播：设备名、IP、端口、版本、锁定状态 |
| 文件 | 0x0020 | `LIST_DIR` | PC→掌机 | 请求目录列表 |
| 文件 | 0x0021 | `DIR_LISTING` | 掌机→PC | 目录内容（名称/大小/类型/修改时间） |
| 文件 | 0x0022 | `DELETE` | PC→掌机 | 请求删除（**需确认**） |
| 文件 | 0x0023 | `DELETED` | 掌机→PC | 删除结果 |
| 文件 | 0x0024 | `RENAME` | PC→掌机 | 请求重命名（**需确认**） |
| 文件 | 0x0025 | `RENAMED` | 掌机→PC | 重命名结果 |
| 文件 | 0x0026 | `MKDIR` | PC→掌机 | 请求新建目录（**需确认**） |
| 文件 | 0x0027 | `MKDIR_OK` | 掌机→PC | 结果 |
| 传输 | 0x0030 | `UPLOAD_START` | PC→掌机 | 声明文件名/大小/校验和（**需确认**） |
| 传输 | 0x0031 | `UPLOAD_DATA` | PC→掌机 | 64KB 二进制数据块 |
| 传输 | 0x0032 | `UPLOAD_END` | PC→掌机 | 传输结束，校验完整性 |
| 传输 | 0x0033 | `UPLOAD_ACK` | 掌机→PC | 应答（含已接收偏移，支持断点续传） |
| 传输 | 0x0034 | `UPLOAD_RESULT` | 掌机→PC | 最终结果 |
| **下载** | **0x0035** | **`DOWNLOAD_START`** | **PC→掌机** | **请求下载某文件（只读，无需确认）** |
| **下载** | **0x0036** | **`DOWNLOAD_DATA`** | **掌机→PC** | **64KB 二进制数据块** |
| **下载** | **0x0037** | **`DOWNLOAD_END`** | **掌机→PC** | **发送结束** |
| **下载** | **0x0038** | **`DOWNLOAD_RESULT`** | **掌机→PC** | **最终结果（含总大小）** |
| 确认 | 0x0040 | `CONFIRM_REQUIRED` | 掌机→PC | 通知 PC「正在等待用户确认，请勿重复操作」 |
| 确认 | 0x0041 | `CONFIRM_RESULT` | 掌机→PC | 用户决策：同意 / 拒绝 / 超时 |
| 错误 | 0x00F0 | `ERROR` | 双向 | 错误码 + 描述 |

> **v1.2 新增 `DOWNLOAD_*` 族**。v1.1 需求 2 写的是"增删改查"，但协议只有 `UPLOAD_*`，
> 缺少「掌机 → PC」方向。补齐后需求才真正闭环：用户可以把掌机上的存档备份回 PC、
> 或从掌机取 ROM 出来。以下载是**只读操作**，按需求 4 的精神仍走弹窗确认（可设置为免确认，
> 但默认确认，与"掌机掌握最终决定权"一致）。
> 断点续传同样支持：`DOWNLOAD_START` 携带 `from_offset`。

### 5.3 确认流程时序

以"删除文件"为例：

```
PC 掌机                        掌机端
 │                              │  ← 用户在此弹出确认框
 │─── DELETE {path} ───────────►│
 │                              │─ 校验路径白名单/黑名单
 │                              │─ 校验锁定状态
 │                              │─ 震动马达轻震 200ms
 │                              │─ 显示确认弹窗
 │                              │─ 25 秒后显示倒计时
 │◄── CONFIRM_REQUIRED ─────────│
 │                              │
 │   （PC 显示"等待掌机确认"）    │  ← 用户按 A 或 B
 │                              │
 │◄── CONFIRM_RESULT{approved} ──│
 │                              │─ 执行 / 或拒绝
 │◄── DELETED{ok} ─────────────│
```

**关键点**：

- **掌机端是决策方**，PC 只是等待方
- **超时 30 秒默认拒绝**，用户没在意的操作自动作废，安全优先
- 弹窗出现 25 秒后显示倒计时提示，让用户知道剩余时间
- 震动马达轻震作为"有请求"的提示，不打扰但能感知
- PC 端在等待期间**必须禁用所有写操作按钮**，避免竞态

### 5.4 自动发现协议

掌机端每 5 秒向 `255.255.255.255:48211` 发送 UDP 广播（`BEACON` 报文）：

```json
{
  "device_name": "RG35XX Pro",
  "device_id": "a3f2c8e1",
  "ip": "192.168.1.105",
  "port": 48200,
  "version": 1,
  "locked": false,
  "base_path": "/mnt/mmc",
  "storage": [
    { "slot": "TF1", "path": "/mnt/mmc",   "free_mb": 18432, "is_current": true  },
    { "slot": "TF2", "path": "/mnt/sdcard", "free_mb": 102400, "is_current": false }
  ]
}
```

**v1.2 变更**：
- 新增 `base_path` 字段 —— 由启动脚本注入的 `BASE_PATH` 环境变量，程序**据此认定自己管理哪张卡**
- `storage[].is_current` 取代 `is_default` —— 明确标出"当前这份程序对应哪张卡"
- 仍保留对 `/mnt/mmc`、`/mnt/sdcard` 的探测，但**仅用于"另一张卡是否存在"的展示**，
  不参与决策（决策只看 `base_path`）

`storage` 是**数组**，长度取决于实际探测到的卡槽数量。单卡设备只返回一个元素，PC 端据此动态渲染 —— 不显示不存在的卡槽行。

**为什么不扫 IP 段**：UDP 广播零配置、不打扰其他设备、不会引起安全软件误报。

**UDP 广播与 WiFi 兼容性风险**：部分企业级 AP 会屏蔽 UDP 广播。**缓解方案**：PC 端同时提供"手动输入 IP"作为兜底入口。这个兜底功能是必须的，不能省。

### 6.3 锁定状态机（A+C 确认机制）

这是本项目最核心的状态设计。**锁定 = 只读**，解锁 = 允许弹窗确认。

```
                    ┌──────────────┐
                    │   锁定状态    │  每次启动初始为锁定
                    │  (只读模式)   │  最小权限原则
                    └──────┬───────┘
                           │
              START 键切换 │
                           ▼
                    ┌──────────────┐
                    │   解锁状态    │
                    │ (可弹窗确认)  │
                    └──────┬───────┘
                           │
        ┌──────────────────┴──────────────────┐
        │                                     │
   收到写请求                            收到写请求
        │                                     │
        ▼                                     ▼
┌───────────────┐                    ┌───────────────┐
│  显示确认弹窗  │                    │  显示确认弹窗  │
│  A=同意 B=拒绝 │                    │  A=同意 B=拒绝 │
└───────┬───────┘                    └───────┬───────┘
        │                                     │
        ▼                                     ▼
   执行操作                             执行操作
   （弹窗消失）                          （弹窗消失）
        │                                     │
        └──────────────┬──────────────────────┘
                       │
              30 秒无响应
                       │
                       ▼
                ┌────────────┐
                │  超时→拒绝  │  安全默认
                └────────────┘
```

**安全设计要点**：

- **每次启动默认锁定**——用户必须主动按 START 解锁，遵循最小权限原则。**解锁状态不跨程序运行持久化**，退出后下次启动回到锁定
- **解锁 ≠ 放行一切**——解锁只是"允许弹窗"，每个写操作仍需逐次按 A 确认
- **超时 30 秒视为拒绝**——考虑到用户可能不在手边，留足时间；但不主动操作就不会误删
- **震动提示**——确认弹窗出现时马达轻震 200ms
- **防连击**——弹窗期间忽略重复请求，避免用户手抖连按
- **UI 状态一致性**——锁定时 PC 端界面所有写按钮置灰，掌机端标题栏常驻显示锁定徽标

### 6.4 传输落地的二次确认（v1.2 修订判定依据）

**v1.1 的错误**：以「目标是否在 `Roms/` 之下」判定是否需要额外警告。这会导致用户传存档时
（实际路径 `saves_RA/Roms/GBA/`）反复看到"写入非默认目录可能影响掌机启动"的红字，
而实际上这是完全安全的操作。用户体验被无谓的警告稀释，真正的危险反而被淹没。

**v1.2 的正确判定**：以「是否触碰**系统关键目录**」判定。

```
                    收到上传/下载请求
                         │
                  查 pathguard 判定分类
                         │
        ┌────────────────┼────────────────┐
        │                │                │
   安全区              警告区           禁止区
  Roms/  saves_RA/   System/  config/  /mnt/vendor
  states_RA/  save/   *.sh（根目录）  /etc /usr /sys

        │                │                │
        ▼                ▼                ▼
   ┌───────────────┐ ┌──────────────┐ ┌──────────────┐
   │  标准确认弹窗   │ │ 目录警告弹窗  │ │  直接拒绝     │
   │  一次确认即可   │ │ + 标准确认    │ │  不弹窗       │
   │  A=同意 B=拒绝  │ │  两次确认     │ │  PC 立即报错  │
   └───────┬───────┘ └──────┬───────┘ └──────────────┘
           │                │
           └────────┬───────┘

无论落在哪，一次传输都**最多需要两次确认**；PC 端等待期间双端均显示"等待确认"状态。

**目录警告弹窗文案示例**（仅警告区触发）：

```
┌────────────────────────────────┐
│   ⚠ 目标目录可能影响掌机启动     │

### 6.5 程序退出机制

退出是主界面的一个菜单项（十字键 + A 选中），不占用独立快捷键，降低误触。

**三种运行状态下的退出行为**：

| 当前状态 | 退出行为 | 说明 |
|---|---|---|
| **空闲**（主界面走马灯） | 直接退出，返回 Apps Center | 无需清理，无待处理事务 |
| **待确认**（屏幕正显示弹窗） | 退出并视为拒绝该请求 | 用户选择退出而非按 A/B，意图明确，不再多问一遍 |
| **传输中**（显示进度条） | 先弹警告，A 确认 / B 取消 | 传输会中断，需清理 `.part` 临时文件 |

```
┌────────────────────────────────┐
│   ⚠ 正在传输文件                │
│                                │
│   game.iso  58%                 │
│   退出会中断传输                │
│                                │
├────────────────────────────────┤
│   [A] 确认退出   [B] 继续传输   │
└────────────────────────────────┘
```

**退出后的收尾动作**：

1. 关闭 TCP 监听与 UDP 广播套接字
2. 清理所有未完成的 `.part` 临时文件
3. 状态复位（含锁定态，下次启动回到锁定）
4. 释放 SDL2 资源，正常 `exit(0)`

### 6.6 卡槽与卡根显示（v1.2 重写）

**v1.1 的做法**：程序启动时探测 `/mnt/mmc`、`/mnt/sdcard` 是否挂载，据此判断 TF1/TF2。

**问题**：探测可能失败（挂载延迟、权限、路径在不同固件版本不同），
一旦失败就会显示错误的卡槽，或让双卡用户看到"TF2 不存在"。

**v1.2 的做法**（与 Grout 一致，已在同批机型实证）：**卡根本身由启动脚本告诉程序**。

```bash
# launcher.sh 里
progdir="$(cd "$(dirname "$0")"; pwd)"
basedir="$(cd "$progdir/../.."; pwd)"   # Roms/APPS -> 卡根
export BASE_PATH="$basedir"
```

程序启动时读 `BASE_PATH` 环境变量，直接就知道 `base_path` 是 `/mnt/mmc` 还是 `/mnt/sdcard`。
挂载探测**降级为纯展示用途**，只用来回答"另一张卡在不在"。

主界面显示：

```
┌────────────────────────────────┐
│  PocketTransfer    [已锁定]     │
│  卡: TF1 (/mnt/mmc)            │  ← 来自 BASE_PATH，一定正确
│  其他: TF2 已挂载              │  ← 探测结果，仅供参考
├────────────────────────────────┤
```

单卡用户只看到 `卡: TF1`，不会误以为设备故障。**双卡用户要把发布包拷到两张卡的
`Roms/APPS/` 下**，各管各的，互不干扰 —— 这是分发时要在说明文档里写清楚的。

### 6.7 中文字体方案（需解决的技术难点）

原厂固件**没有中文字体**。可选方案：

| 方案 | 体积 | 效果 | 评价 |
|---|---|---|---|
| 打包完整 CJK TTF | 10-20MB | 完美 | ❌ 占内存，浪费 |
| 提取子集字体 | 200-500KB | 完美 | ✅ **推荐** |
| 烧录进 ROM | 极小 | 完美 | ❌ 有法律风险 |
| SDL_ttf + 精简 TTF | 500KB | 完美 | ✅ 推荐，配合子集提取 |

**采用方案（v1.4 修订）**：

✅ **不需要子集化，直接用原厂字体 `/mnt/vendor/bin/default.ttf`。**

实机确认（2026-10-05）：原厂固件**自带中文字体**，位于 `/mnt/vendor/bin/default.ttf`，
支持中文显示，Pillow 的 `ImageFont.truetype` 可直接加载。

> 原文的"必须自备字体 + fonttools 子集化"基于"固件无中文字体"这一**错误假设**（社区传闻）。
> 本机是 Ubuntu 22.04 原厂固件，字体齐全。

**降级预案**（万一某固件版本字体缺失）：用 `fonttools` 对开源字体（思源黑体 / Noto Sans SC）
做子集化，只保留项目实际用到的约 300-500 个汉字，产出 200-400KB 的 TTF 打进 `assets/`。

中文显示在 UI 中是刚需（用户是中文使用者），所以必须在启动时**验证字体可用**，
失败时明确报错而不是显示方块。

## 七、安全设计

| 风险 | 防护措施 |
|---|---|
| 路径穿越攻击（`../../etc/passwd`） | 掌机端强制路径规范化 + 三区分类（安全/警告/禁止），拒绝一切越界路径 |
| 系统文件被误删 | 只读根文件系统天然保护；额外硬编码禁止路径黑名单（`/etc`、`/usr`、`/sys`、`/proc`、`/mnt/vendor`） |
| 未授权访问 | 首次连接需在掌机端确认，设备 ID + IP 双重校验 |
| 中间人窃听 | v1 版本用**预共享密钥**（PSK）做 HMAC 完整性校验；TLS 留作 v2 升级项 |
| 传输中断残留文件 | 临时文件写 `.part` 后缀，传输成功才改名，失败自动清理 |
| 磁盘写满 | 传输前检查可用空间，不足则拒绝并告知 |
| 写到系统区导致掌机变砖 | 三区分类：系统关键目录额外警告（两次确认）；禁止区直接拒绝 |
| 删掉系统启动脚本导致无法开机 | TF1 根目录下的 `*.sh` / `config*` 归入警告区，二次确认 |

### 7.1 路径管控：三区分类（v1.2 重写）

```
安全区（一次确认即可写入）
  Roms/            saves_RA/        states_RA/
  save/            bios/            Imgs/
  Uart/            APPS/ 下的应用自身目录

警告区（两次确认：目录警告 + 标准确认）
  System/          config/          root 下的 *.sh / *.ini / *.cfg
  TF 卡根目录下的系统配置文件
  其他未在黑名单中的系统相关目录

禁止区（直接拒绝，不弹窗，PC 立即返回错误）
  /mnt/vendor   ← 原厂固件系统核心（appfs，只读）
  /etc  /usr  /sys  /proc  /dev  /boot  /root
  任何超出 BASE_PATH 的路径（路径穿越）
```

### 7.2 落地目录规则（v1.2 修订）

| 情形 | 行为 |
|---|---|
| 目标在安全区 | 一次确认即可 |
| 目标在警告区 | **二次确认**（目录警告 + 标准确认） |
| 目标在禁止区 | **直接拒绝**，不弹窗，PC 端立即返回错误 |
| 目标超出 `BASE_PATH`（路径穿越等） | **直接拒绝**，记录日志并告警 |

**与 v1.1 的差异**：v1.1 是「`Roms/` 白名单 + 其他全部二次确认」，v1.2 改为
「系统关键目录黑名单 + 其余一次确认」。这样存档目录（`saves_RA/` 等）不再被误判为危险，
而真正会影响掌机启动的目录仍受保护。

**说明**：v1 不做完整 TLS。理由是同一家庭 WiFi 场景下威胁模型有限，而 PSK + 路径分类已能挡住主要风险。v2 引入 TLS（用 OpenSSL 或 mbedTLS，掌机端有现成库）。

### 8.1 部署结构（v1.2 修正 —— 重要）

**原厂固件的 launcher 只扫描 `Roms/APPS/` 下的 `*.sh` 文件，目录不会被列为应用。**
这一点在 rommapp/grout 仓库的 `scripts/Anbernic/Grout.sh` 注释里有明确说明（原文：
"the payload lives in the sibling folder (directories are not listed as apps)"）。

因此 v1.1 的目录结构是**不可用的**，正确结构如下：

```
Roms/
├── APPS/
│   ├── PocketTransfer.sh        # ← 启动脚本，必须直接放在 APPS 根目录
│   ├── PocketTransfer/          # ← 负载目录（启动脚本的兄弟目录）
│   │   ├── main.py              #   入口脚本（Python 3.10，v1.4 修订）
│   │   ├── sdl_display.py       #   SDL2 显示后端
│   │   ├── fb.py                #   裸 fb 后端（兜底）
│   │   ├── boot.py              #   崩溃诊断层
│   │   ├── assets/
│   │   │   └── icon.png         #   菜单图标
│   │   └── boot.log             #   运行时日志（脚本自动追加 + 轮转）
│   └── Imgs/
│       └── PocketTransfer.png   # ← 菜单图标（注意是 APPS/Imgs/，不是 Roms/Imgs/）
```

> **v1.4 修订**：不再需要 `lib/`（复用固件自带 SDL2）、不再需要 `font_cjk.ttf`
> （用原厂 `/mnt/vendor/bin/default.ttf`）、不再有 aarch64 可执行文件（Python 脚本直接跑）。
> 日志文件名是 `boot.log`（不是 `logs/stdout.log`）。
>
> ⚠️ **已实机验证：这个结构是正确的**（菜单能列出应用、能启动、能显示、能退出）。

**launcher.sh 完整内容**（阶段 0 直接可用，已按 Grout 实证调整）：

```bash
#!/bin/bash
# PocketTransfer launcher for the Anbernic stock OS.
# The stock launcher lists every *.sh in Roms/APPS and runs it with $0 set to its path,
# so the payload lives in the sibling "PocketTransfer" folder.
# 本脚本系「实际部署并验证通过」的版本（v1.4）。

set -u
progdir="$(cd "$(dirname "$0")" && pwd)"
basedir="$(cd "$progdir/../.." && pwd)"    # Roms/APPS -> 卡根
APPDIR="$progdir/PocketTransfer"

export BASE_PATH="$basedir"                 # 卡根（程序据此认定管哪张卡）
export PYSDL2_DLL_PATH="/usr/lib"           # ★ 必须！原厂 5 个 .sh 都有这一行
export LD_LIBRARY_PATH="/usr/lib:/mnt/vendor/lib:${LD_LIBRARY_PATH:-}"

# 日志：追加 + 轮转（不要用 exec > 截断，会丢历史）
LOG="$APPDIR/boot.log"
[ -f "$LOG" ] && [ "$(stat -c%s "$LOG")" -gt 262144 ] && mv "$LOG" "$LOG.1"

# 环境自检：失败时明确报错，不静默退出
[ -d "$APPDIR" ]         || { echo "缺应用目录 $APPDIR"; exit 1; }
[ -f "$APPDIR/main.py" ] || { echo "缺 main.py"; exit 1; }
PY="$(command -v python3)" || { echo "系统未找到 python3"; exit 1; }

"$PY" "$APPDIR/main.py" >> "$LOG" 2>&1
exit 0
```

**四个必须点，缺一不可**：

| # | 做什么 | 不做的后果 |
|---|---|---|
| 1 | 脚本放 `Roms/APPS/PocketTransfer.sh` | 菜单里根本不出现这个应用 |
| 2 | `basedir` 自算并 export `BASE_PATH` | 程序不知道管哪张卡，双卡用户显示错 |
| 3 | 日志重定向到 `boot.log`（追加 + 轮转） | 崩溃/缺库无任何痕迹，无法调试 |
| 4 | `export PYSDL2_DLL_PATH="/usr/lib"` | **找不到 libSDL2，程序秒退**（原厂 5 个 .sh 都有） |

**绝对不能做的事**（用户硬边界）：

❌ 调 `setmode.py` 切显示模式（曾导致 SIGBUS）· ❌ `mkdir -p` 建应用目录（掩盖发布包不完整）
❌ `exec >` 覆盖日志 · ❌ kill 任何进程 · ❌ 写 `/tmp/.next` · ❌ remount · ❌ 建软链 · ❌ 写 sysfs

## 十一、环境适配与分发设计

程序将分享给其他用户，需适配不同卡布局与固件版本。

### 卡根与卡槽

**卡根由启动脚本决定，不由程序探测**（见 6.6 / 8.1）：

```
用户把发布包拷进 TF1 的 Roms/APPS/  →  程序管 /mnt/mmc
用户把发布包拷进 TF2 的 Roms/APPS/  →  程序管 /mnt/sdcard
双卡用户：两份都拷，各管各的，互不干扰
```

PC 端界面动态显示：

```
检测到双卡（当前 TF1）              检测到单卡
┌──────────────────────┐    ┌──────────────────────┐
│ 卡: TF1  /mnt/mmc     │    │ 卡: TF1  /mnt/mmc     │
│ 其他: TF2 已挂载      │    │ 其他: 无              │
└──────────────────────┘    └──────────────────────┘
```

**探测不到第二张卡时，TF2 那行完全不显示**（不做成灰色禁用项，避免用户误以为设备故障）。

### 落地目录规则

```
用户选中 TF1  →  文件落到 /mnt/mmc/ 下（按 6.4 三区分类决定确认次数）
用户选中 TF2  →  文件落到 /mnt/sdcard/ 下
```

### PC 端标题栏常驻信息

```
┌────────────────────────────────────────────────┐
│  RG35XX Pro  ·  已连接：TF1  ·  [已锁定]       │
├────────────────────────────────────────────────┤
```

同时显示设备名、当前操作卡槽、掌机锁定状态。用户随时知道自己操作的是哪张卡、掌机是否处于可写状态。

### 记住上次传输目录

PC 端本地保存最近一次成功传输的目标路径。下次打开文件面板时**自动定位到该目录**，用户不必逐层点击进入。

- 存储位置：Win11 端 `%AppData%\PocketTransfer\config.json`
- 仅保存路径字符串，不保存任何文件内容
- 路径失效（目录被删或换卡）时自动回退到该卡的 `Roms/` 根目录

## 十二、附：技术分析（参考）

### Grout 技术栈（重要参考样本，已在同批机型验证）

rommapp 官方 RomM 客户端 Grout，是**目前唯一在 Anbernic 原厂固件上跑通的生产级第三方应用**，
对本项目参考价值极高：

- 技术栈：**Go + go-sdl2（veandco/go-sdl2）+ go-evdev**
- 部署：`Roms/APPS/Grout.sh` + 兄弟目录 `Roms/APPS/grout/` + `Roms/APPS/Imgs/`
- 卡根：启动脚本自算 `basedir` 并 export `BASE_PATH`
- 日志：脚本内 `exec >logs/stdout.log 2>&1`
- 依赖：`export LD_LIBRARY_PATH` 指向自带 `lib/`
- 按键映射：`cfw/anbernic/input_mappings/anbernic.json` 用 evdev joystick button code

**对我们的启示**：
1. **SDL2 路线是被验证过的**——v1.1 把 SDL2 交叉编译列为"高风险"过于保守，
   实际有同机型生产级先例，风险等级下调为「中高」
2. **部署结构必须照抄 Grout**（8.1），这是 v1.1 最实质的错误
3. **卡根自算优于挂载探测**——少一个失败模式
4. Grout 本身打包了完整运行时（体积大），我们走相反路线：复用 SDL2，二进制 < 500KB，
   在 1GB 内存设备上启动速度和内存占用都更好

### RixelHK 技术分析

- 双平台（Android APK + Linux 版），Linux 版 ~18-22MB
- 闭源，原作者已删库，被 PortMaster 开发者逆向发现索要大量网络与设备信息
- 因 ROM 版权问题被 Anbernic 官方下架
- 技术栈无公开证据，体积 18MB 远大于原生 C/C++ 程序，结合"一份代码双平台"特征，
  **大概率是 Flutter 或同类跨平台框架**

### 已知硬件问题 → ✅ 已查明（2026-10-05）

**玩家报告 RG35XX Pro 摇杆"在部分模拟器中不灵" —— 根因已查明，不是硬件问题。**

实机 `EVIOCGBIT` + 事件监听（`tools/probe-input.py`）确认：

| 输入类型 | 走的事件 | 说明 |
|---|---|---|
| 所有按键（A/B/X/Y/L/R/SELECT/START/MENUF/音量） | **`EV_KEY`** | code 304-312 / 314-315 / 114-115 |
| **摇杆 + 十字方向** | **`EV_ABS`** ★ | `ABS_RX`(3) 水平 / `ABS_RY`(4) 垂直，值域 ±3700 |

**"不灵"的真正原因**：那些模拟器只读 `EV_KEY`，把 `EV_ABS` 事件整个丢掉了，
所以摇杆完全没反应。

**两个必须处理的细节**：
1. **负值是补码**：`-3700` 在 evdev 里读出来是 `4294963596`，必须 `value - (1<<32)` 转换
2. **摇杆持续发同值事件**，必须去重（记录上次方向，只有变化才产生事件），并设死区

**结论**：不需要"参考社区映射自行标定" —— 直接用 `tools/probe-input.py` 实测即可，
已实现于 `main.py`（`KEYMAP` / `ABS_AXES` / `STICK_DEADZONE` / `axis_direction()`）。
